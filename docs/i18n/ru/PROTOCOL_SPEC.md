## 1. Аннотация

Aether — это децентрализованный протокол ячеистых сетей (mesh), разработанный для сред с нестабильным или отсутствующим подключением к интернету. Он обеспечивает многоскачковую маршрутизацию пакетов через разнородные транспорты ближней связи (Bluetooth Low Energy, Wi-Fi Direct, NearLink), сквозное шифрование с использованием согласования ключей на основе X3DH и симметричного ращета, устойчивую к задержкам доставку с промежуточным хранением (store-and-forward), а также механизм экстренной SOS-рассылки методом флуда. Протокол не зависит от транспорта: любой физический уровень, способный отправлять и принимать массивы байт между узлами, является допустимым транспортом Aether. Узлы идентифицируются по Universal Hardware Identifiers (UHID) и аутентифицируются посредством идентификационных ключей Ed25519. Aether предназначен в качестве универсального сетевого уровня — каждое приложение в экосистеме регистрирует сервисы Aether, а узлы без подключения к интернету достигают широкой сети через шлюзовые узлы (gateway), обеспечивающие мост между mesh-трафиком и интернетом.

## 2. Формат пакета

> Сверено 2026-05-05 с эталонной реализацией на C# в
> `src/AetherNet.Core/Protocol/PacketSerializer.cs`
> и 17 fixture-случаями в `fixtures/expected/`.

### 2.1. Структура MeshPacket на уровне wire

Каждое сообщение Aether инкапсулируется в `MeshPacket`. Поля располагаются
на wire в **точно** следующем порядке:

| Смещение | Поле             | Тип                             | Размер     | Примечания |
|----------|------------------|---------------------------------|------------|------------|
| 0        | ProtocolVersion  | uint8                           | 1          | `1` = без подписи (устаревший), `2` = с подписью (текущий) |
| 1        | Type             | uint8                           | 1          | Перечисление типов пакетов (см. §2.4) |
| 2        | Id               | UUID, RFC 4122 big-endian       | 16         | Идентификатор пакета для дедупликации. Порядок байт **big-endian**, а НЕ смешанный порядок .NET Guid по умолчанию. |
| 18       | Priority         | uint8                           | 1          | Уровень приоритета (0 = обычный, 255 = SOS). **Wire-поле занимает 1 байт; значения >255 должны быть ограничены.** |
| 19       | Ttl              | int32, little-endian            | 4          | Время жизни, уменьшается на каждом прыжке. **4-байтный int32**, а НЕ 1-байтный uint8 — допустимы значения до ~2³¹-1. |
| 23       | TimestampMs      | int64, little-endian            | 8          | Миллисекунды Unix epoch (UTC). |
| 31       | SourceUhid Len   | uint16, little-endian           | 2          | Длина `SourceUhid` в байтах UTF-8. Максимум 65535. |
| 33       | SourceUhid       | UTF-8 bytes                     | N          | UHID отправителя; пустое значение допустимо, но нетипично. |
| 33+N     | DestinationUhid Len | uint16, little-endian        | 2          | Длина `DestinationUhid` в байтах UTF-8. |
| ...      | DestinationUhid  | UTF-8 bytes                     | M          | UHID получателя; пустая строка означает широковещательную рассылку. |
| ...      | PacketNonce Len  | uint16, little-endian           | 2          | Длина `PacketNonce` в байтах. Стандартное значение: 8. |
| ...      | PacketNonce      | bytes                           | P          | Криптографически случайный nonce для предотвращения воспроизведения. |
| ...      | Payload Len      | int32, little-endian            | 4          | Длина `Payload` в байтах. Отрицательные значения являются ошибкой. |
| ...      | Payload          | bytes                           | Q          | Данные приложения. Интерпретация зависит от `Type`. |
| ...      | Signature Len    | uint16, little-endian           | 2          | Длина `Signature` в байтах. 0 (без подписи) или 64 (Ed25519). |
| ...      | Signature        | bytes                           | R          | Подпись Ed25519 над подписываемыми данными (см. §2.3). |

**Ширина префиксов длины** варьируется в зависимости от поля — `SourceUhid`, `DestinationUhid`,
`PacketNonce` и `Signature` используют **2-байтные (uint16)** префиксы длины;
`Payload` использует **4-байтный (int32)** префикс длины, поскольку полезная нагрузка может превышать
64 КиБ.

### 2.2. Минимальный размер пакета

При всех полях переменной длины, равных нулю (UHID нулевой длины, nonce нулевой длины,
полезная нагрузка нулевой длины, подпись нулевой длины), размер на wire составляет:

```
1 (version) + 1 (type) + 16 (id) + 1 (priority) + 4 (ttl)
  + 8 (timestamp) + 2 (src len) + 2 (dst len)
  + 2 (nonce len) + 4 (payload len) + 2 (sig len)
= 43 bytes
```

Цифры 50 байт / 52 байта в ранних черновиках этой спецификации были неверными.

### 2.4. Формирование подписываемых данных

Подпись (поле `Signature` на wire) вычисляется над отдельной
канонической последовательностью байт — **не** над самими байтами wire. Это
позволяет структуре wire развиваться без нарушения подписей и позволяет
промежуточным узлам верифицировать целостность, не видя открытой полезной нагрузки
(подписывается только её хеш SHA-256).

Подписываемая последовательность байт является конкатенацией:

```
PacketNonce (8 bytes)
|| TimestampMs            (8 bytes, little-endian int64)
|| Type                   (4 bytes, little-endian int32)
|| SourceUhidLength       (4 bytes, little-endian int32)
|| SourceUhid             (UTF-8 bytes)
|| DestinationUhidLength  (4 bytes, little-endian int32)
|| DestinationUhid        (UTF-8 bytes)
|| SHA-256(Payload)       (32 bytes)
|| Ttl                    (4 bytes, little-endian int32)
|| Priority               (4 bytes, little-endian int32, clamped to [0,255])
```

> Обратите внимание на намеренное отличие от структуры wire в §2.1: подписываемые
> данные используют **4-байтный int32** для `Type`, `Length`, `Ttl` и `Priority`,
> тогда как wire использует соответственно 1-байтный / 2-байтный / 4-байтный / 1-байтный форматы.
> Это намеренно — подписываемая форма переносима между языками и
> использует поля фиксированной ширины; форма wire компактна ради экономии BLE PDU.
> Реализации должны ограничивать `Priority` диапазоном `[0,255]` перед кодированием в
> подписываемые байты, иначе получатель (видящий байт wire 0..255)
> получит другой подписываемый буфер, и верификация завершится неудачей.

Эталонная реализация находится в `src/AetherNet.Security/Services/
PacketSigningService.cs::BuildSignableData` и является обязательным чтением при
портировании.

## 3. Алгоритм маршрутизации

Aether использует реактивный протокол маршрутизации на основе AODV (Ad-hoc On-demand Distance Vector), расширенный криптографической аутентификацией маршрутов и взвешенным выбором маршрута с учётом QoS.

### 3.1. Запрос маршрута (RREQ)

Когда узлу необходимо отправить пакет в пункт назначения, для которого у него нет маршрута, он инициирует запрос маршрута:

1. Инициатор создаёт `MeshPacket` с `Type = RouteRequest`, устанавливает `SourceUhid` в своё значение, `DestinationUhid` — в целевое, а `TTL = 7` (по умолчанию).
2. Пакет широковещательно передаётся всем непосредственно подключённым узлам.
3. Каждый промежуточный узел, получивший RREQ:
   a. Проверяет, видел ли он уже этот RREQ по `Id` пакета. Если да — молча отбрасывает пакет (дедупликация). Кеш дедупликации удерживает до `DeduplicationCacheSize` записей (по умолчанию 10 000) и полностью очищается при достижении лимита.
   b. Устанавливает **обратный маршрут** к инициатору RREQ. В обратном маршруте в качестве следующего прыжка записывается UHID узла, от которого был получен RREQ. Количество прыжков вычисляется как `DefaultTtl - packet.Ttl + 1`.
   c. Если узел ЯВЛЯЕТСЯ назначением — формирует RREP (см. Раздел 3.2).
   d. Если у него есть действующий маршрут к назначению — МОЖЕТ сформировать RREP от имени назначения.
   e. В противном случае уменьшает TTL и повторно рассылает RREQ.
4. Инициатор ожидает RREP с таймаутом **5 000 мс** (`RouteTimeoutMs`). Если RREP не поступает — обнаружение маршрута завершается неудачей.

### 3.2. Ответ маршрута (RREP)

Когда назначение (или промежуточный узел с действующим маршрутом) формирует ответ маршрута:

1. Создаётся `MeshPacket` с `Type = RouteReply`, где `SourceUhid` установлен в узел назначения, а `DestinationUhid` — в инициатора RREQ.
2. **ТРЕБОВАНИЕ БЕЗОПАСНОСТИ:** RREP ДОЛЖЕН быть подписан идентификационным ключом Ed25519 узла назначения. Подпись охватывает стандартные подписываемые данные (Раздел 2.3). Это предотвращает отравление маршрутов злоумышленными промежуточными узлами.
3. RREP направляется по обратному маршруту, установленному при распространении RREQ.
4. Каждый промежуточный узел, перенаправляющий RREP:
   a. Верифицирует подпись RREP по открытому ключу заявленного источника (если он известен). При неудаче верификации RREP отбрасывается и записывается предупреждение.
   b. Устанавливает **прямой маршрут** к источнику RREP (узлу назначения), используя отправителя RREP в качестве следующего прыжка.
   c. Уменьшает TTL и перенаправляет к инициатору RREQ.
5. Когда RREP достигает инициатора, ожидающий запрос маршрута (отслеживаемый через `TaskCompletionSource`) разрешается с установленным маршрутом.

### 3.3. Поддержка маршрутов

- **Истечение срока действия по TTL:** Каждая запись маршрута содержит метку времени `ExpiresAt`, равную `now + 300 секунд` (`RouteExpirySeconds`). Маршруты не обновляются неявно — после истечения срока они должны быть повторно установлены через новый цикл RREQ/RREP.
- **Периодическая очистка:** Сервис протокола выполняет периодическую операцию heartbeat (по умолчанию каждые 300 секунд). В каждом цикле он удаляет истёкшие маршруты как из `ConcurrentDictionary` в памяти, так и из резервного хранилища SQLite.
- **Очистка дедупликации RREQ:** Набор просмотренных ID RREQ очищается, когда он превышает `DeduplicationCacheSize` (по умолчанию 10 000) записей.

### 3.4. Качество маршрута и QoS

Каждая `RouteEntry` содержит `QualityScore` в диапазоне [0, 100], инициализированный значением 50 для вновь обнаруженных маршрутов. Оценка учитывает:

- **Количество прыжков:** Меньшее число прыжков, как правило, означает более быстрый маршрут.
- **Задержка:** Измеренное время приёма-передачи, когда доступно.
- **Надёжность узла:** Оценка надёжности узла следующего прыжка (см. Раздел 3.5).

Узлы, участвующие в системе поощрений через чаевые, получают QoS-надбавку к оценке качества маршрута. Это мягкое предпочтение: узлы, не платящие чаевые, всегда получают обслуживание, однако постоянные плательщики могут наблюдать незначительно лучший выбор маршрута. Уровни надбавки:

| Уровень | Порог стабильности | Надбавка QoS |
|---------|--------------------|--------------|
| Bronze  | 25                 | +5           |
| Silver  | 50                 | +10          |
| Gold    | 75                 | +20          |

### 3.5. Оценка надёжности узла

Каждому известному узлу присваивается оценка надёжности в диапазоне [0, 100], инициализированная значением 50 (`DefaultReliabilityScore`). Оценка корректируется на основе наблюдаемого поведения:

| Событие              | Изменение |
|----------------------|-----------|
| Успешная ретрансляция| +2        |
| Неудачная ретрансляция| -5       |
| SOS-ретрансляция     | +5        |
| Фрагмент обслужен    | +1        |
| Ошибка обслуживания фрагмента | -10 |

Оценки надёжности сохраняются в SQLite и загружаются в память при запуске. Оценка влияет на выбор маршрута: предпочтение отдаётся маршрутам через более надёжные узлы.

## 4. Обмен ключами

> Сверено 2026-05-05 с эталонной реализацией на C# в
> `src/AetherNet.Security/Services/SignalProtocolService.cs` и
> corpus fixture между языками в `fixtures/signal/`. Реализация на C#
> включает полный X3DH + Double Ratchet (Signal §3 + §5) над X25519. Go,
> Python, TypeScript, Rust, Swift и Kotlin портированы на тот же конверт
> и дают побайтово идентичные результаты на уровне fixture X3DH и KDF_RK.
> C теперь также включает полную машинерию сессии (X3DH + жизненный цикл
> OPK/SPK + Double Ratchet в `c/src/signal_protocol.c`, с двухузловыми
> сквозными тестами в `c/tests/test_signal_session.c`), а не только примитивы.
> Где данный раздел расходится с кодом — код является авторитетным источником;
> зафиксируйте проблему в `OPEN_ISSUES.md`.

Aether реализует **X3DH** (Extended Triple Diffie-Hellman, Signal §3) для
асинхронного установления сессии, незамедлительно за которым следует **Signal
Double Ratchet** (Signal §5) для обеспечения постоянной прямой секретности и
безопасности после компрометации. Весь криптографический код сессии работает над Curve25519:
**X25519** (RFC 7748) для ECDH и **Ed25519** (RFC 8032) для подписи.

### 4.1. Идентификационные ключи

При первом запуске каждый узел генерирует **две** долгосрочные пары ключей (без XEdDSA;
более простая схема с двумя ключами — то, что реализовано в каждой имплементации):

- **Пара ключей Ed25519** — 32-байтовый seed (закрытый ключ), 32-байтовый открытый ключ.
  Используется для подписи пакетов (§2.4), `SignedPreKeySignature` (§4.3),
  аутентификации RREP (§3.2) и подписей чаевых.
- **Пара ключей X25519** — 32-байтовые «сырые» закрытый и открытый ключи. Используются для
  четырёх DH-операций X3DH (§4.4).

Ссылка: `SignalProtocolService.InitializeIdentityKeys`. Закрытые ключи
хранятся только на устройстве; открытые ключи публикуются в `PreKeyBundle`.

Для *верификации подписи* входящих пакетов поддерживается 30-дневное окно миграции P-256 → Ed25519 — см. §7.5. Сами пакеты pre-key используют только X25519 на wire.

### 4.2. Выбор кривой

X3DH и Double Ratchet используют исключительно **X25519**. P-256 *не* используется
при установлении сессии ни в одной из текущих реализаций. Более ранний черновик этой
спецификации описывал ECDH на P-256; этот текст предшествует переводу всего семейства
на X25519 от 2026-05-05 и более не является актуальным.

### 4.3. Пакет pre-key

Пакет pre-key публикуется так, чтобы инициатор мог установить
сессию без присутствия ответчика онлайн (Signal §3.4):

```
PreKeyBundle {
    Uhid:                   string      // Universal Hardware Identifier узла
    IdentityKey:            byte[32]    // Долгосрочный открытый ключ Ed25519 (для подписи)
    IdentityKeyX25519:      byte[32]    // Долгосрочный открытый ключ X25519 (ECDH)
    PreKeyId:               int32       // Идентификатор одноразового pre-key
    PreKey:                 byte[32]    // Открытый ключ X25519 одноразового pre-key (OPK)
    SignedPreKeyId:         int32       // Идентификатор подписанного pre-key
    SignedPreKey:           byte[32]    // Открытый ключ X25519 подписанного pre-key (SPK)
    SignedPreKeySignature:  byte[64]    // Ed25519(IdentityKey, SignedPreKey)
}
```

Ссылка: `AetherNet.Security.Models.PreKeyBundle`. Контракт wire-формата одинаков
для всех 8 языков.

**Пул одноразовых pre-key (OPK).** Каждый ответчик поддерживает пул из
`OpkPoolSize` (по умолчанию 100, в соответствии с опубликованными рекомендациями Signal) ключей X25519
OPK. При генерации пакета берётся следующий неиспользованный идентификатор из очереди FIFO, затем
пул пополняется до целевого размера. Каждый OPK используется ровно один раз: ответчик удаляет
и обнуляет закрытую половину при получении первого сообщения PreKey, ссылающегося на его идентификатор.
Параллельные инициаторы, соревнующиеся за один и тот же идентификатор OPK, увидят ровно один
успешный вызов `EstablishResponderSession` под `_preKeyLock`; проигравший получит `CryptographicException`.

Ссылка: `SignalProtocolService.TopUpOpkPoolNoLock` (строки 494–518),
`SignalProtocolService.EstablishResponderSession` (строки 636–718). Семантика пула
проверяется в `tests/AetherNet.Core.Tests/PreKeyPoolTests.cs`.

**Ротация подписанного pre-key (SPK).** SPK генерируется лениво при первом
вызове bundle и повторно используется в последующих вызовах, чтобы параллельные инициаторы,
получающие пакеты до выполнения X3DH, не аннулировали пакеты друг друга.
Периодическая ротация SPK (Signal §3.3 рекомендует еженедельно) является явной
операцией, а не побочным эффектом генерации пакета.

Идентификаторы pre-key извлекаются из `RandomNumberGenerator.GetInt32(1, int.MaxValue)`
с явным повтором при коллизии (до 64 попыток перед выдачей исключения).

### 4.4. Установление сессии (X3DH)

Полный X3DH (Signal §3.3) выполняется на стороне инициатора. Вычисляются четыре DH-операции
над X25519:

```
DH1 = DH(IK_A, SPK_B)    // долгосрочная взаимная аутентификация
DH2 = DH(EK_A, IK_B)     // эфемерный ключ инициатора привязывается к идентичности ответчика
DH3 = DH(EK_A, SPK_B)    // эфемерный ключ инициатора привязывается к SPK ответчика
DH4 = DH(EK_A, OPK_B)    // эфемерный ключ инициатора привязывается к OPK ответчика
```

где `IK_A` / `IK_B` — идентификационные ключи X25519, `EK_A` — свежий
эфемерный ключ X25519, сгенерированный только для этой сессии, `SPK_B` — подписанный
pre-key ответчика, `OPK_B` — одноразовый pre-key ответчика. Начальный корневой ключ:

```
RK_0 = HKDF-SHA256(
    ikm  = DH1 || DH2 || DH3 || DH4,
    salt = (по умолчанию — пустой),
    info = UTF8("aether-x3dh-root-v1"),
    L    = 32 bytes)
```

Константа `info` `aether-x3dh-root-v1` идентична во всех реализациях и зафиксирована
в `fixtures/signal/expected/x3dh_basic.json` (поле `root_key_hex`).

Ссылка: `SignalProtocolService.ProcessPreKeyBundleAsync` (строки
554–626). Путь верификации:
случай `x3dh_basic` из `fixtures/signal/inputs.json` →
`fixtures/signal/expected/x3dh_basic.json`.

**Верификация пакета.** До выполнения любых DH-операций инициатор верифицирует
`SignedPreKeySignature` по `IdentityKey` с помощью Ed25519. Неудачная
верификация вызывает `CryptographicException`, и пакет отбрасывается.
Размеры открытых ключей проверяются по `X25519Service.PublicKeySize` (32);
некорректные пакеты отклоняются.

**Первичная инициализация сессии.** По завершении `ProcessPreKeyBundleAsync` создаётся
`SignalSession` со следующими полями:

- `RootKey = RK_0`
- `MyEphemeralPriv / MyEphemeralPub = EK_A` — Signal-каноническая интеграция X3DH ↔
  Double-Ratchet: эфемерный ключ X3DH инициатора становится его первой парой ключей DH-ращета (`DHs`).
- `RemoteEphemeralPub = SPK_B` — подписанный pre-key ответчика рассматривается
  как начальный ключ ращета узла (`DHr`).
- `SendChainKey = null`, `RecvChainKey = null` — оба ключа цепочки выводятся
  лениво при первой отправке / первом приёме с DH-ращетом.
- `PendingPreKeyMessage = true` — флаг того, что следующий исходящий вызов
  `EncryptAsync` ДОЛЖЕН создать сообщение PreKey (`MessageType=1`).

Все выходы DH и конкатенированный общий секрет обнуляются в блоке
`finally` через `CryptographicOperations.ZeroMemory`.

**Запрет небезопасной отправки.** Если `EncryptAsync` вызывается для узла
без сессии, вызов выбрасывает `InvalidOperationException`. Запасного пути на основе
UHID не существует. Предполагается, что хосты ставят сообщение в очередь
(см. `MessagingService` + `SignalMessageEnvelopeCipher`) и повторяют попытку после
завершения установления сессии.

### 4.5. Double Ratchet (Signal §5)

Каждая сторона поддерживает ротирующуюся пару ключей ращета X25519 (`DHs`) и копию
последнего виденного открытого ключа ращета узла (`DHr`). При каждом сообщении
отправитель публикует свой текущий открытый ключ `DHs`; всякий раз, когда получатель
обнаруживает новый `DHr`, он выполняет **шаг DH-ращета**, переключая ключ цепочки
через `KDF_RK(RK, DH(myDHs, newDHr))` — повторно выводя как корневой ключ, так и свежий
ключ цепочки.

#### 4.5.1. KDF_RK

`KDF_RK` — это HKDF-SHA256 над 64-байтовым блоком, разделённым 32+32 на новый
корневой ключ и новый ключ цепочки:

```
out      = HKDF-SHA256(
    ikm  = DH_output,
    salt = current_root_key,
    info = UTF8("aether-ratchet-rk-v1"),
    L    = 64 bytes)
new_RK   = out[0..32]
new_CK   = out[32..64]
```

Ссылка: `SignalProtocolService.KdfRk` (строки 857–868). Зафиксировано в
случае `kdf_rk_basic` из `fixtures/signal/inputs.json` →
`fixtures/signal/expected/kdf_rk_basic.json`.

#### 4.5.2. Симметрический ращет

В соответствии с Signal §5.1, ключи сообщений и ключи цепочки выводятся из ключа
цепочки с помощью HMAC-SHA256 с однобайтовым разделением домена:

```
message_key   = HMAC-SHA256(chain_key, 0x01)
new_chain_key = HMAC-SHA256(chain_key, 0x02)
```

Ссылка: `SignalProtocolService.RatchetChainKey` (строки 876–881).
Зафиксировано случаями `ratchet_step_basic` и
`ratchet_step_three_iterations` в `fixtures/signal/inputs.json`.

Более ранний черновик этой спецификации описывал `messageKey =
HMAC-SHA256(chain_key, counter_bytes)` и отдельное продвижение `chain_key
через HMAC(chain_key, 0x01)`. Это не соответствовало Signal и никогда не было реализовано;
заменено каноническим разделением 0x01/0x02.

#### 4.5.3. Шаг DH-ращета при получении

Инициируется, когда `SenderEphemeralKeyX25519` входящего сообщения отличается
от кешированного `RemoteEphemeralPub` (сравнение с постоянным временем выполнения).

1. Сохраняем исходящий счётчик как `PreviousChainCount` (Signal §5: PN), чтобы
   узел мог вычислить пропущенные ключи через границу.
2. Сбрасываем `SendCounter` и `RecvCounter` до 0; устанавливаем новый `RemoteEphemeralPub`.
3. Выводим новую цепочку получения: `(RK', CKr) = KDF_RK(RK, DH(myDHs, newDHr))`.
4. Обнуляем закрытую часть старого `myDHs`; генерируем новую пару ключей X25519.
5. Выводим новую цепочку отправки: `(RK'', CKs) = KDF_RK(RK', DH(newDHs, newDHr))`.

Ссылка: `SignalProtocolService.DhRatchetReceive` (строки 726–772).

#### 4.5.4. Ленивый вывод цепочки отправки

Первая отправка инициатора выполняет **полушаг** вместо полного
DH-ращета — X3DH уже установил `DHs` и `DHr`, поэтому нужно вывести только
цепочку отправки:

```
(RK', CKs) = KDF_RK(RK, DH(myDHs, DHr))
```

`DHs` при этом *не* ротируется. Ротация выполняется только при истинном шаге
DH-ращета на стороне получателя.

Ссылка: `SignalProtocolService.DhRatchetSendOnly` (строки 780–796).

#### 4.5.5. Пропущенные ключи сообщений

Когда сообщения приходят не по порядку, ключ сообщения для каждого пропущенного счётчика
кешируется в `SkippedMessageKeys` с ключом `(Hex(remoteEphPub):counter)`.
Привязка к открытому ключу удалённого узла существенна — внеочередные сообщения из
предыдущей цепочки (другого `DHr`) могут поступить после шага DH-ращета и требуют
собственного набора ключей для каждой цепочки.

Ограничения:

- Пропуск более `MaxSkippedKeys` (1000) записей в одном разрыве
  вызывает `CryptographicException` и принудительное повторное установление сессии.
- При пересечении границы DH-ращета получатель сначала пропускает до
  `PreviousChainCount` ключей на *старой* цепочке, затем выполняет шаг
  DH-ращета перед выводом ключей на новой цепочке.

Ссылка: `SignalProtocolService.SkipMessageKeys` (строки 804–830) и
цикл пропуска в decrypt (строки 366–388).

### 4.6. Формат зашифрованной полезной нагрузки

```
EncryptedPayload {
    Ciphertext:                     byte[]      // Шифртекст AES-256-GCM || 16-байтовый тег
    Nonce:                          byte[12]    // Nonce AES-GCM, случайно сгенерированный
    MessageType:                    int32       // 0 = обычное, 1 = PreKey
    SenderUhid:                     string      // UHID отправителя
    Counter:                        int32       // Ns отправителя в текущей цепочке

    // Double Ratchet — заполняется в КАЖДОМ сообщении:
    SenderEphemeralKeyX25519:       byte[32]    // Текущий открытый ключ DHs отправителя
    PreviousChainCount:             int32       // Signal §5: PN

    // X3DH — заполняется только в сообщениях PreKey (MessageType == 1):
    InitiatorIdentityKeyX25519:     byte[32]?   // Открытый ключ IK_X25519 инициатора
    UsedSignedPreKeyId:             int32       // Идентификатор использованного SPK
    UsedOneTimePreKeyId:            int32       // Идентификатор использованного OPK
    InitiatorEphemeralKeyX25519:    byte[32]?   // УСТАРЕЛО — равно SenderEphemeralKeyX25519
}
```

Ссылка: `AetherNet.Security.Models.EncryptedPayload` (строки 55–66 файла
`SecurityModels.cs`). Поле `InitiatorEphemeralKeyX25519` является
псевдонимом для обратной совместимости с pre-Double-Ratchet wire-конвертом и
равно `SenderEphemeralKeyX25519` в сообщениях PreKey; новые потребители
должны его игнорировать.

Параметры AES-GCM: 256-битный ключ, 96-битный nonce (`AesNonceSize = 12`),
128-битный тег (`AesTagSize = 16`), тег конкатенирован с шифртекстом.
Ключи сообщений обнуляются в блоках `finally` сразу после шифрования/дешифрования AES-GCM.

## 5. Требования транспортного уровня

Aether не зависит от транспорта. Любой физический канал связи, удовлетворяющий контракту `ITransportService`, может участвовать в mesh.

### 5.1. Контракт интерфейса ITransportService

Каждая реализация транспорта ДОЛЖНА предоставлять следующее:

**Свойства:**

| Свойство             | Тип    | Описание |
|----------------------|--------|----------|
| `Name`               | string | Удобочитаемый идентификатор (например, "BLE", "Wi-Fi Direct", "NearLink") |
| `IsAvailable`        | bool   | Доступен ли транспорт для использования на данном устройстве |
| `MaxBandwidthBps`    | int64  | Максимальная пропускная способность в байтах в секунду |
| `MaxRangeMeters`     | int32  | Максимальная дальность связи в метрах |
| `PowerCostRelative`  | int32  | Относительное энергопотребление (1 = низкое, 10 = высокое) |
| `MaxConcurrentPeers` | int32  | Максимальное количество одновременных подключений к узлам |

**Методы:**

| Метод              | Сигнатура | Описание |
|--------------------|-----------|----------|
| `SendAsync`        | `Task<bool> SendAsync(string peerUhid, byte[] data, CancellationToken)` | Отправить массив байт конкретному узлу. Возвращает true при успехе. |
| `SendStreamAsync`  | `Task<bool> SendStreamAsync(string peerUhid, Stream data, CancellationToken)` | Отправить поток данных узлу (для больших передач, голоса, видео). |
| `IsConnected`      | `bool IsConnected(string peerUhid)` | Проверить, активно ли соединение с узлом. |

**События:**

| Событие        | Сигнатура | Описание |
|----------------|-----------|----------|
| `DataReceived` | `EventHandler<(string SenderUhid, byte[] Data)>` | Инициируется при поступлении данных от узла. |

### 5.2. Алгоритм выбора транспорта

`TransportManager` выбирает оптимальный транспорт для каждого пакета на основе:

1. **Доступность:** Рассматриваются только транспорты, где `IsAvailable == true`.
2. **Размер полезной нагрузки:** Если размер полезной нагрузки не превышает `BleMaxPayloadBytes` (1 024 байта), для энергоэффективности предпочитается BLE. Для больших полезных нагрузок предпочтительнее Wi-Fi Direct.
3. **Взвешивание по энергозатратам:** Среди доступных транспортов для обычного трафика предпочитаются более низкие значения `PowerCostRelative`. Для высокоприоритетных пакетов (SOS, голос) это предпочтение может быть переопределено.
4. **Подключение к узлу:** Если транспорт уже имеет активное соединение с целевым узлом (`IsConnected` возвращает true), он предпочтительнее для избежания накладных расходов на установление соединения.
5. **Резервный вариант:** Если ни один локальный транспорт не может достичь цели, пакет ставится в очередь для ретрансляции через сервер посредством AetherNetAPI.

### 5.3. Эталонные транспорты

| Транспорт    | МаксПропускнаяСп.  | МаксДальность | Энергозатраты | МаксУзлов | Примечания |
|-------------|---------------------|---------------|---------------|-----------|------------|
| BLE 5.0     | ~2 Мбит/с           | 100 м         | 1             | 7         | Основное обнаружение + малые пакеты |
| Wi-Fi Direct| ~250 Мбит/с         | 200 м         | 5             | 8         | Большие передачи, потоковая передача, голос |
| NearLink    | ~900 Мбит/с         | 200 м         | 3             | 16        | Huawei/HiSilicon, высокая пропускная способность |

**Ограничение полезной нагрузки BLE:** Пакеты, превышающие 1 024 байта (`BleMaxPayloadBytes`), автоматически перенаправляются на Wi-Fi Direct или NearLink. BLE используется для объявлений об обнаружении, малых управляющих пакетов (RREQ/RREP, маячки присутствия) и низкополосного обмена сообщениями.

Таймаут соединения **Wi-Fi Direct** составляет 10 000 мс (`WifiDirectTimeoutMs`) с максимумом 8 одновременных узлов (`MaxWifiDirectPeers`).

## 6. Протокол обнаружения

### 6.1. BLE-реклама

Узлы Aether обнаруживают друг друга преимущественно через BLE-рекламу. Для предотвращения долгосрочного отслеживания через статические идентификаторы протокол применяет два механизма конфиденциальности: ротирующиеся Service UUID и ключи разрешения идентичности (IRK).

**Цикл рекламы:** 2 секунды сканирования, 8 секунд паузы (`BleScanOnMs`/`BleScanOffMs`). Интервал рекламы — 1 000 мс (`BleAdvertiseIntervalMs`). К интервалу сканирования добавляется случайное дрожание 0–2 000 мс (`BleScanJitterMaxMs`) для предотвращения обнаружения временных паттернов.

**Таймаут узла:** Узел, не обнаруженный повторно в течение 30 секунд, считается потерянным (событие `PeerLost`).

### 6.2. Ротирующийся Service UUID

Для предотвращения долгосрочной BLE-дактилоскопии Service UUID, используемый в рекламе, ротируется каждые 15 минут (`BleUuidRotationSeconds = 900`):

```
window     = floor(unix_timestamp_seconds / 900)
hmac       = HMAC-SHA256(rotation_key, little-endian-int64(window))
service_uuid = format_as_uuid(hmac[0..15])
```

`rotation_key` — это 32-байтовый ключ, генерируемый единожды для каждого узла и хранящийся в защищённом хранилище. Все узлы Aether, использующие один и тот же ключ ротации, будут выводить один и тот же UUID для данного временного окна, обеспечивая взаимное обнаружение без раскрытия постоянного идентификатора.

Статический резервный UUID (`A3E7-1001-0001-0000-000000000000`) поддерживается в течение 90 дней при переходе со схемы без ротации.

### 6.3. Ключ разрешения идентичности (IRK)

Каждый узел генерирует 128-битный ключ разрешения идентичности (IRK), хранящийся в защищённом хранилище. IRK передаётся доверенным узлам при обмене ключами.

**Генерация Resolvable Private Address (RPA):**

1. Вычисляем `prand = HMAC-SHA256(IRK, window_bytes)[0..2]` (3 байта).
2. Устанавливаем два старших бита `prand[0]` равными `01` (флаг RPA согласно спецификации BLE).
3. Вычисляем `hash = AES-128-ECB(IRK, pad(prand))`, где `prand` занимает байты 13–15 16-байтового ввода с нулевым дополнением.
4. Формируем RPA: `hash[0..2] || prand[0..2]` (всего 6 байт).

**Разрешение RPA:** Узел, обладающий IRK узла, может проверить, принадлежит ли наблюдаемый RPA данному узлу, пересчитав хеш из компонента `prand` RPA. Время разрешения составляет приблизительно O(N), где N — количество известных IRK, производительность составляет ~0,1 мс для 100 узлов.

RPA ротируется в том же 15-минутном цикле, что и Service UUID.

### 6.4. Близость на основе Geohash

Узлы опционально кодируют своё местоположение в виде geohash. В целях конфиденциальности geohash усекается до 4 символов, обеспечивая разрешение приблизительно 39 км × 20 км. Такая детализация достаточна для:

- Обнаружения каналов по близости
- Эпидемической маршрутизации DTN (репликация в направлении последнего известного geohash-региона получателя)
- Географического контекста SOS-оповещений

Полноточный geohash никогда не передаётся через mesh. Только усечённая форма распространяется, и только когда уровень конфиденциальности узла это допускает (`PrivacyLevel.Full` или `PrivacyLevel.Partial`).

## 7. Модель безопасности

### 7.1. Модель угроз

Aether предполагает следующие возможности противника:

- **Пассивное прослушивание:** Противник может наблюдать все BLE-объявления и mesh-трафик в радиусе радиосвязи.
- **Активное внедрение:** Противник может внедрять, модифицировать или воспроизводить пакеты.
- **Sybil-атака:** Противник может создавать множество поддельных идентичностей узлов.
- **Избирательный отказ в обслуживании:** Противник может избирательно сбрасывать пакеты в роли узла ретрансляции.

### 7.2. Что защищено

| Свойство | Уровень защиты | Механизм |
|----------|----------------|----------|
| Содержание сообщения | Полная конфиденциальность | AES-256-GCM с ключами на каждое сообщение (Раздел 4.5) |
| Идентичность отправителя | Частичная | UHID виден в заголовках пакета; BLE-адрес ротируется (Раздел 6) |
| Идентичность получателя | Частичная | UHID назначения виден в маршрутизируемых пакетах; широковещательные пакеты имеют пустое назначение |
| Метаданные маршрутизации | Минимальная | Промежуточные узлы видят UHID источника/назначения и TTL |
| Порядок сообщений | Защищён | Счётчики в симметрическом ращете предотвращают перестановку |
| Целостность сообщения | Полная | Подпись Ed25519 на каждом пакете (v2) |

### 7.3. Устойчивость к атакам

**Атаки воспроизведения:**
Каждый пакет содержит 8-байтовый криптографически случайный nonce и метку времени с точностью до миллисекунды. Узлы ретрансляции поддерживают кеш дедупликации пар `(SenderUhid, NonceValue)` со временем жизни 5 минут (`MaxPacketAgeSeconds = 300`). Пакет с дублирующимся nonce от того же отправителя отбрасывается. Пакеты с метками времени старше 5 минут отклоняются независимо от nonce.

Кеш дедупликации nonce очищается каждые 60 секунд. Истёкшие записи (старше 5 минут) удаляются.

**Атака «человек посередине» (MITM):**
- Пакеты Route Reply ДОЛЖНЫ содержать действительную подпись Ed25519 от заявленного узла назначения. Промежуточные узлы не могут подделать RREP, поскольку не обладают закрытым ключом назначения.
- Пакеты pre-key содержат `SignedPreKeySignature` (Ed25519) над `SignedPreKey`, привязывая эфемерный ключ ECDH к долгосрочной идентичности.
- Установление сессии (Раздел 4.4) криптографически привязывает сессию к идентичностям обеих сторон через шаг верификации pre-key.

**Sybil-атаки:**
- Оценка надёжности каждого узла начинается с 50 и корректируется на основе наблюдаемого поведения (Раздел 3.5). Новосозданные Sybil-узлы не имеют накопленной репутации.
- Узлы с низкими оценками надёжности (близкими к 0) получают низкий приоритет при выборе маршрута.
- Алгоритм эпидемической маршрутизации DTN использует близость по geohash и историю успешности ретрансляции для выбора целей репликации, затрудняя привлечение трафика Sybil-узлами без реального вклада в ретрансляцию.

**Атаки флудом:**
- TTL уменьшается на каждом прыжке, и пакеты с TTL = 0 отбрасываются. Стандартный TTL равный 7 ограничивает радиус поражения любой широковещательной передачи.
- Дедупликация RREQ по ID пакета предотвращает усиление через широковещательные штормы. Кеш дедупликации сбрасывается при превышении `DeduplicationCacheSize` (по умолчанию 10 000) записей.
- SOS-рассылки ограничены 3 в час на узел (Раздел 8).

### 7.4. Обнуление ключей

Все промежуточные криптографические материалы немедленно обнуляются после использования:

- `sharedSecret` из согласования ключей ECDH: обнуляется после вывода HKDF.
- `messageKey` из ращета цепочки: обнуляется после шифрования/дешифрования AES-GCM.
- `skippedKey` из внеочерёдного дешифрования: обнуляется после использования и удаляется из карты.
- Производные `RootKey`, `SendChainKey`, `RecvChainKey`: обнуляются из контекста установления (сессия сохраняет собственные копии).

Обнуление выполняется с помощью `CryptographicOperations.ZeroMemory`, гарантированно не оптимизируемой компилятором.

### 7.5. Миграция с P-256 на Ed25519

Протокол поддерживает 30-дневное переходное окно с ключей идентичности ECDSA P-256 (Protocol Version 1) на Ed25519 (Protocol Version 2):

1. Пакеты Protocol Version 1 (без подписи) принимаются в период перехода.
2. Верификация подписи сначала пытается использовать Ed25519. Если открытый ключ длиннее 32 байт (что указывает на DER-кодированный ключ P-256), используется резервная верификация ECDSA P-256.
3. По истечении 30-дневного окна пакеты Protocol Version 1 отклоняются.
4. Узлы, не прошедшие миграцию, должны повторно инициализироваться с новой идентичностью Ed25519.

### 7.6. Учёт юрисдикции

Протокол определяет уровни юрисдикций для учёта различных правовых требований в отношении шифрования и ячеистых сетей:

| Уровень | Поведение | Примеры юрисдикций |
|---------|-----------|--------------------|
| 1       | Свободная работа | South Africa, Kenya, Ghana |
| 2       | Изменённая работа | Nigeria, India, EU, US, UK |
| 3       | Только mesh (высокий риск) | China, Russia, Iran, UAE, Myanmar |
| 4       | Неизвестно (только mesh по умолчанию) | Все остальные |

Выбор уровня влияет на доступность функций (например, финансовые функции/чаевые могут быть отключены на уровне 3), но не ослабляет шифрование. Сквозное шифрование применяется всегда вне зависимости от юрисдикции.

## 8. SOS-рассылка

Механизм SOS представляет собой двухпутёвый экстренный флуд, предназначенный для ситуаций, когда пользователь находится в опасности и ему необходимо достичь ближайших mesh-узлов и/или интернета одновременно.

### 8.1. Параметры рассылки

| Параметр  | Значение | Описание |
|-----------|----------|----------|
| TTL       | 15       | Вдвое больше стандартного по умолчанию (7), что обеспечивает более широкое распространение |
| Priority  | 999      | Максимальный приоритет; вытесняет весь остальной трафик в очередях ретрансляции |
| Ограничение частоты | 3/час | Лимит на узел для предотвращения злоупотреблений |
| Destination | пустой | Широковещательная рассылка всем узлам (без конкретного назначения) |

### 8.2. Алгоритм флуда

1. Инициатор формирует SOS-пакет с `Type = SosBroadcast`, `TTL = 15`, `Priority = 999` и пустым `DestinationUhid`.
2. Полезная нагрузка кодируется в JSON и содержит:
   ```json
   {
       "broadcast_id": "UUID",
       "broadcast_type": "sos",
       "message": "optional text",
       "latitude": -33.9249,
       "longitude": 18.4241,
       "geohash": "k3vn"
   }
   ```
3. **Двухпутёвая отправка:** SOS отправляется одновременно через:
   - **Mesh-флуд:** Широковещательная рассылка всем подключённым узлам через все доступные транспорты.
   - **API-вызов:** Отправляется в AetherNetAPI для серверного распространения и моста к PanikAPI (отправка SMS/email).
4. Оба пути являются независимыми (fire-and-forget). В случае сбоя API-вызова mesh-флуд продолжается независимо.

### 8.3. Поведение при ретрансляции

При получении узлом SOS-пакета:

1. Проверяем дедупликацию по `Id` пакета. Если уже видели — молча отбрасываем.
2. Десериализуем полезную нагрузку и инициируем событие `SosReceived` для локального UI.
3. Добавляем оповещение в список активных оповещений.
4. Если `TTL > 1` — уменьшаем TTL и **повторно рассылаем ВСЕМ узлам** независимо от состояния таблицы маршрутизации. SOS-пакеты обходят нормальную маршрутизацию — они флудируют безусловно.

### 8.4. Ограничение частоты

Каждый узел поддерживает скользящее окно недавних меток времени рассылок. Перед инициацией нового SOS:

1. Удаляем из очереди записи старше 1 часа.
2. Если очередь содержит 3 и более записей (`MaxSosBroadcastsPerHour`) — рассылка отклоняется.
3. При успешной отправке текущая метка времени добавляется в очередь.

Ограничение частоты применяется только к инициированию SOS-рассылок, но не к их ретрансляции.

### 8.5. Мост SOS-PanikAPI

SOS-рассылки, полученные через mesh, могут быть перенаправлены в PanikAPI для традиционного экстренного реагирования (SMS контактам, email-оповещения). Напротив, экстренные сессии PanikAPI могут транслироваться в mesh для информирования сообщества. Предотвращение петель достигается путём маркировки источника (`direct` или `mesh_forward`) и флага `internet_forwarded` на mesh-рассылках.

## 9. DTN Store-and-Forward

Подсистема Delay-Tolerant Networking (DTN) обеспечивает доставку сообщений, когда между отправителем и получателем не существует сквозного пути. Бандлы хранятся на промежуточных узлах и пересылаются по мере изменения доступности соединений.

### 9.1. Формат бандла

```
DtnBundle {
    Id:                 UUID        // Уникальный идентификатор бандла
    SenderUhid:         string      // UHID инициатора
    RecipientUhid:      string      // UHID предполагаемого получателя
    EncryptedPayload:   byte[]      // Содержимое с сквозным шифрованием
    Priority:           enum        // Low(0), Normal(1), High(2), Sos(3)
    Status:             enum        // Pending(0), InCustody(1), Delivered(2), Expired(3), Failed(4)
    CopyCount:          int32       // Текущее количество копий в сети (инициализируется значением 1)
    MaxCopies:          int32       // Максимально допустимое количество копий (по умолчанию: 3)
    SenderGeohash:      string?     // Усечённый geohash отправителя на момент создания
    RecipientLastGeohash: string?   // Последний известный geohash получателя (для маршрутизации по близости)
    HopCount:           int32       // Количество выполненных передач хранения
    CreatedAt:          timestamp
    ExpiresAt:          timestamp   // По умолчанию: CreatedAt + 72 часа
}
```

### 9.2. Жизненный цикл бандла

1. **Создание:** Отправитель создаёт бандл с зашифрованной полезной нагрузкой (зашифрованной через Signal-сессию с получателем). `Status = Pending`, `CopyCount = 1`.
2. **Немедленная попытка доставки:** Отправитель сначала пытается использовать прямую mesh-маршрутизацию (RREQ/RREP). Если маршрут существует — бандл доставляется немедленно и `Status` переходит в `Delivered`.
3. **Попытка ретрансляции через сервер:** При сбое mesh-маршрутизации отправитель пытается ретранслировать через AetherNetAPI. Если сервер может достичь получателя (или поставить сообщение в очередь) — доставка успешна.
4. **Store-and-forward:** При сбое как mesh-, так и серверной ретрансляции бандл остаётся в локальном хранилище (статус `Pending`) до следующего цикла сканирования доставки.

### 9.3. Цикл сканирования доставки

Периодическое сканирование запускается каждые 60 секунд (`DtnScanIntervalSeconds`):

1. Загружаем все ожидающие бандлы из SQLite (источник достоверных данных).
2. Для каждого ожидающего бандла:
   a. Пытаемся найти mesh-маршрут к получателю.
   b. Пытаемся использовать серверную ретрансляцию.
   c. При сбое обоих вариантов и `CopyCount < MaxCopies` пытаемся выполнить эпидемическую репликацию (Раздел 9.4).
3. Удаляем истёкшие бандлы (`ExpiresAt <= now`).

### 9.4. Эпидемическая маршрутизация

Когда прямая доставка и серверная ретрансляция обе завершаются неудачей, бандлы реплицируются на ближайшие узлы с использованием эпидемической маршрутизации:

1. `EpidemicRoutingService` выбирает цели репликации из текущего списка узлов.
2. При выборе цели учитывается:
   - **Близость по geohash:** Узлы, чей geohash ближе к последнему известному geohash получателя, являются предпочтительными.
   - **История ретрансляций:** Узлы с более высокими оценками надёжности предпочтительнее.
   - **Бюджет копий:** Репликация прекращается при `CopyCount >= MaxCopies` (по умолчанию: 3).
3. Каждая репликация отправляет пакет `DtnBundle` выбранному узлу.
4. При получении DTN-сервис узла вызывает `AcceptCustodyAsync`.

### 9.5. Передача хранения

При получении узлом DTN-бандла, предназначенного другому узлу:

1. **Проверка ёмкости:** Узел проверяет текущее количество бандлов по отношению к `DtnMaxBundlesPerNode` (50). При заполнении — хранение отклоняется.
2. **Принятие:** Статус бандла устанавливается в `InCustody`, счётчик прыжков увеличивается, и бандл сохраняется в SQLite.
3. **Запись хранения:** Создаётся `CustodyRecord`, документирующая передачу (от кого, кому, метка времени).
4. **Увеличение счётчика копий:** `CopyCount` бандла увеличивается в постоянном хранилище.
5. **Подтверждение:** Пакет `DtnCustodyAck` с `Accepted = true` отправляется обратно передающему узлу.
6. Принявший узел становится ответственным за попытки доставки в последующих циклах.

### 9.6. Квитанция о доставке

Когда предполагаемый получатель получает DTN-бандл:

1. Статус бандла обновляется до `Delivered`.
2. `DtnDeliveryReceipt` отправляется обратно исходному отправителю через mesh-маршрутизацию (с резервной серверной ретрансляцией):
   ```
   DtnDeliveryReceipt {
       BundleId:               UUID
       RecipientUhid:          string
       TotalHops:              int32
       TotalCustodyTransfers:  int32
       DeliveredAt:            timestamp
   }
   ```
3. При получении квитанции отправитель удаляет бандл из своего хранилища и инициирует событие `BundleDelivered`.
4. Квитанция также синхронизируется с AetherNetAPI для аналитики.

### 9.7. Истечение срока действия бандла

- Стандартный TTL бандла — 72 часа (`DtnBundleTtlHours`).
- Истёкшие бандлы очищаются в ходе периодического цикла сканирования доставки.
- Бандлы в статусе `Expired` или `Delivered` удаляются как из кеша в памяти, так и из SQLite.

### 9.8. Ограничения ёмкости

| Параметр                | По умолчанию | Описание |
|-------------------------|--------------|----------|
| `DtnBundleTtlHours`     | 72           | Максимальный срок жизни бандла |
| `DtnMaxCopies`          | 3            | Максимальное количество копий бандла в сети |
| `DtnMaxBundlesPerNode`  | 50           | Максимальное количество бандлов, хранимых одним узлом |
| `DtnScanIntervalSeconds`| 60           | Частота цикла сканирования доставки |

## 10. Потоковое видео

> **Статус по состоянию на 2026-05-05 — проектирование + каркас C#, без работающего конвейера кодека.**
> Типы пакетов `StreamAnnounce` (11), `StreamSegment` (12),
> `StreamSubscribe` (13), `StreamUnsubscribe` (14), `VideoCall` (27),
> `VideoSignaling` (28), `VideoFrame` (31), `ScreenShare` (32) определены
> на уровне wire и передаются по cross-language fixture corpus.
> Модуль C# `AetherNet.Streaming` включает интерфейсы, модели и скелетные
> сервисы (`StreamingService`, `VideoCallService`, `WatchTogetherService`),
> подключающие стыки маршрутизации/DI и юникастное распределение сегментов —
> но фактическое кодирование/декодирование видео к ним не привязано. Остальные
> 7 языков имеют только wire-типы. Целевая архитектура описана в
> `docs/adaptive-secure-streaming-spec.md`.
> Воспринимайте приведённый ниже текст как спецификацию того, что эти сервисы БУДУТ
> реализовывать; пробелы в производственной готовности см. в `OPEN_ISSUES.md`.


Aether поддерживает три видеорежима: P2P-видеозвонки, групповое видео (неограниченное число участников с динамической топологией) и живые трансляции. Все видеофреймы шифруются с помощью Signal Protocol и подписываются с помощью Ed25519.

### 10.1. Матрица возможностей транспортов

Перед инициацией видеозвонка инициатор запрашивает транспортный уровень для определения наилучшего доступного соединения с узлом. Транспорт определяет возможное качество видео:

| Транспорт   | Поддержка видео | Макс. разрешение | Рекомендуемый кодек | Макс. битрейт | Watch-Together |
|-------------|----------------|-----------------|---------------------|---------------|----------------|
| BLE | Нет (только аудио) | — | — | 64 Кбит/с | Только sync-пакеты |
| NearLink | Лёгкое | 360p | H.265 | 800 Кбит/с | SharedFile + StreamFromHost |
| WiFi Direct | Полное | 1080p | H.264 | 3000 Кбит/с | Все режимы |
| Internet | Полное | 720p | H.264 | 1500 Кбит/с | Все режимы |
| CircleLink | Нет (только аудио) | — | — | 64 Кбит/с | Только sync-пакеты |

Если единственным доступным транспортом является BLE или CircleLink, сервис видеозвонков автоматически понижает режим до голосового вызова.

### 10.2. Видеокодеки

| Значение перечисления | Кодек | Случай использования |
|----------------------|-------|---------------------|
| 0 | H.264 | По умолчанию. Широкая поддержка, хорошее сжатие. |
| 1 | H.265 | Лучшее сжатие. Используется в NearLink (ограниченная полоса пропускания). |
| 2 | VP8 | Альтернатива без роялти. |

### 10.3. Разрешения видео

| Значение перечисления | Разрешение | Типичный битрейт |
|----------------------|------------|-----------------|
| 0 | AudioOnly | 64 Кбит/с (Opus) |
| 1 | 360p | 800 Кбит/с |
| 2 | 480p | 1200 Кбит/с |
| 3 | 720p | 1500 Кбит/с |
| 4 | 1080p | 3000 Кбит/с |

### 10.4. Процесс P2P видеозвонка

1. **Проверка возможностей**: Инициатор запрашивает `GetVideoCapabilityAsync(peerUhid)` для определения наилучшего транспорта, максимального разрешения и рекомендуемого кодека.
2. **Предложение (offer)**: Инициатор отправляет пакет `VideoSignaling` (тип 28) с `SignalType = Offer`, включающий предпочтительный кодек, максимальное разрешение и максимальный битрейт.
3. **Ответ/Отказ (answer/reject)**: Вызываемый отвечает либо `SignalType = Answer` (согласование кодека до наименьшего общего знаменателя), либо `SignalType = Reject`.
4. **Активный вызов**: Оба узла обмениваются пакетами `VideoCall` (тип 27), содержащими NAL-блоки H.264/H.265/VP8. Каждый фрейм включает порядковый номер для буферизации джиттера и флаг ключевого кадра.
5. **Демонстрация экрана**: Любая сторона может переключить демонстрацию экрана. `VideoSignaling` с `SignalType = ScreenShareStart/Stop` уведомляет узел. Фреймы демонстрации экрана используют `PacketType.ScreenShare` (тип 32), но тот же конвейер обработки.
6. **Завершение вызова**: Любая сторона отправляет `VideoSignaling` с `SignalType = Bye`.

Все полезные нагрузки сигнализации и фреймов шифруются с помощью Signal Protocol (сессия X3DH). Зашифрованная полезная нагрузка сериализуется как JSON-кодированный `EncryptedPayload` в поле `MeshPacket.Payload`.

### 10.5. Автомат состояний видеозвонка

```
  Initiating ──► Ringing ──► Active ──► Ended
                   │                      ▲
                   ├──► Rejected ─────────┘
                   └──► Failed ───────────┘
```

Состояния: `Initiating(0)`, `Ringing(1)`, `Active(2)`, `OnHold(3)`, `Ended(4)`, `Failed(5)`, `Rejected(6)`.

### 10.6. Групповое видео

Групповые видеосессии поддерживают неограниченное число участников. Топология динамически выбирается в зависимости от числа участников:

- **FullMesh** (2–3 участника): Каждый участник отправляет один поток каждому другому участнику. Простой вариант с низкой задержкой.
- **SFU** (4 и более участников, порог: `SfuThresholdParticipants = 4`): Один узел избирается ретранслятором SFU. Каждый участник отправляет один поток ретранслятору, который распределяет его всем остальным. Узел-ретранслятор зарабатывает чаевые через поощрительный уровень.

Переключение топологии происходит автоматически: при подключении 4-го участника сессия переходит от FullMesh к SFU. При выбытии участников и снижении числа ниже 4 происходит обратный переход.

Групповые видеофреймы используют `PacketType.VideoFrame` (тип 31). В режиме SFU фреймы отправляются на UHID узла-ретранслятора, который их ретранслирует.

### 10.7. Буфер джиттера

Видеобуфер джиттера работает независимо от голосового буфера джиттера (обрабатывающего 20-мс фреймы Opus):

- **Диапазон**: минимум 60 мс, максимум 500 мс.
- **Адаптивная глубина**: Отслеживает межкадровый джиттер через экспоненциальное скользящее среднее (EMA). Глубина буфера = 2 × оценка джиттера, ограниченная диапазоном [60, 500] мс.
- **Осведомлённое о ключевых кадрах отбрасывание**: При переполнении буфера сначала отбрасываются некачественные кадры (P/B). I-фреймы (ключевые кадры) никогда не отбрасываются — они необходимы для восстановления декодера.
- **Обработка пропусков**: При обнаружении разрыва в последовательности буфер пропускает до следующего доступного ключевого кадра вместо бесконечного ожидания.

### 10.8. Типы сигнализации видео

| Значение перечисления | Тип | Описание |
|----------------------|-----|----------|
| 0 | Offer | Инициация видеозвонка с предпочтением кодека/разрешения |
| 1 | Answer | Принятие вызова с согласованными параметрами |
| 2 | Reject | Отклонение вызова |
| 3 | Bye | Завершение вызова |
| 4 | Upgrade | Запрос повышения качества (например, транспорт улучшился) |
| 5 | Downgrade | Запрос снижения качества (например, упала полоса пропускания) |
| 6 | ScreenShareStart | Узел начал демонстрацию экрана |
| 7 | ScreenShareStop | Узел прекратил демонстрацию экрана |

### 10.9. Модель шифрования

| Режим | Шифрование | Распределение ключей |
|-------|------------|---------------------|
| P2P видеозвонок | Signal Protocol на каждый фрейм | Согласование ключей X3DH |
| Групповое видео | Ключ группового канала (AES-GCM) | Распределяется через Signal Protocol при создании сессии |
| Демонстрация экрана | Как в родительском режиме вызова | Наследуется от сессии видеозвонка |

## 11. Watch Together

> **Статус по состоянию на 2026-05-05 — проектирование + каркас C#, та же зрелость, что и §10.**
> Типы пакетов `WatchSync` (29), `WatchReaction` (30),
> `WatchChunkRequest` (33), `TorrentMetadata` (34) определены на wire и
> протестированы с помощью fixture. `AetherNet.Streaming.WatchTogetherService` предоставляет
> координационный каркас (состояние сессии, распространение sync-команд через
> `IMeshSender`, вспомогательные функции компенсации RTT); приём BitTorrent, расчёт
> SDPKT через ChipIn и загрузка фрагментов от узлов не реализованы ни на одном
> языке. Воспринимайте приведённый ниже текст как целевой протокол; документ по проектированию
> `docs/adaptive-secure-streaming-spec.md` охватывает ту же тему более подробно.


Watch Together обеспечивает синхронизированное воспроизведение медиа группой mesh-узлов. Хост имеет эксклюзивное управление воспроизведением (play, pause, seek, speed). Sync-команды содержат метки времени настенных часов для компенсации RTT.

### 11.1. Режимы просмотра

| Значение перечисления | Режим | Поток данных | Требования к транспорту |
|----------------------|-------|--------------|------------------------|
| 0 | SharedFile | Только sync-пакеты (< 100 байт каждый) | Любой (работает через BLE) |
| 1 | StreamFromHost | P2P-передача фрагментов (использует P2pContentService) | WiFi Direct или Internet |
| 2 | BitTorrent | Mesh + внешний рой через шлюзовые узлы | WiFi Direct или Internet |

### 11.2. Режим SharedFile

Оба участника имеют один и тот же файл (сопоставление по хешу содержимого SHA-256). Обмен происходит только пакетами `WatchSync`. Это наиболее экономичный режим по полосе пропускания, работающий через BLE.

1. Хост создаёт сессию просмотра с `contentHash` (SHA-256 файла).
2. Участники присоединяются и сообщают `IsReady = true`, когда проигрыватель загружен.
3. Сессия начинается, когда ВСЕ участники сообщают о готовности.
4. Хост отправляет команды play/pause/seek/speed как пакеты `WatchSync` (тип 29).
5. Получатели применяют компенсацию RTT: `adjustedPosition = commandPosition + (wallClockNow - commandWallClock) / 2`.

### 11.3. Режим StreamFromHost

Файл есть только у хоста. Хост создаёт `ContentManifest` (повторно используя P2P-систему контента), а участники скачивают фрагменты через mesh.

- Выбор фрагментов использует стратегию `SequentialFromPosition` (не `RarestFirst`): приоритет отдаётся фрагментам впереди текущей позиции воспроизведения, затем обратное заполнение для сидирования.
- Цель буфера: 30 секунд вперёд (`WatchTogetherBufferAheadSeconds`).
- Авто-пауза: Если буфер ЛЮБОГО участника опускается ниже 10 секунд (`WatchTogetherMinBufferSeconds`), сессия автоматически ставит всех участников на паузу с sync-командой `BufferUnderrun`. Воспроизведение возобновляется, когда все участники имеют достаточный буфер (`BufferReady`).
- По мере загрузки фрагментов зрители становятся сидерами для других зрителей (роевая раздача в стиле BitTorrent внутри mesh).

### 11.4. Режим BitTorrent

Участник делится файлом `.torrent` или magnet-ссылкой в групповом чате. Пакет `TorrentMetadata` (тип 34) распространяет информацию о торренте всем участникам сессии.

**Мост Mesh-to-Swarm:**
- Шлюзовые узлы (узлы с интернетом) загружают части из внешнего роя BitTorrent.
- Шлюзовые узлы повторно шифруют загруженные части для распространения через mesh и раздают mesh-узлам.
- Mesh-узлы без интернета получают части от шлюзовых узлов и друг от друга.
- Механизм P2P-контента переводит между моделью частей BitTorrent и моделью фрагментов Aether.

После накопления достаточного буфера контента начинается совместный просмотр с использованием того же sync-протокола, что и в режиме SharedFile.

### 11.5. Автомат состояний сессии просмотра

```
  WaitingForReady ──► Playing ◄──► Paused
        │                │           │
        │                ▼           │
        │            Buffering ──────┘
        │                │
        └────────────► Ended
```

Состояния: `WaitingForReady(0)`, `Buffering(1)`, `Playing(2)`, `Paused(3)`, `Ended(4)`.

### 11.6. Типы sync-команд

| Значение перечисления | Тип | Описание |
|----------------------|-----|----------|
| 0 | Play | Возобновить воспроизведение с указанной позиции |
| 1 | Pause | Пауза в указанной позиции |
| 2 | Seek | Переход к указанной позиции |
| 3 | Speed | Изменение скорости воспроизведения |
| 4 | BufferUnderrun | Авто-пауза — буфер участника критически мал |
| 5 | BufferReady | Возобновление — все участники имеют достаточный буфер |

### 11.7. Компенсация RTT

Sync-команды содержат поле `WallClockMs` (миллисекунды Unix epoch). При обработке sync-команды получателем:

1. `rtt = receiverWallClock - commandWallClock`
2. `networkDelay = rtt / 2`
3. Для команд Play и BufferReady: `adjustedPosition = commandPosition + networkDelay`
4. Для команд Pause и Seek: позиция применяется точно (корректировка не нужна, так как воспроизведение останавливается/прыгает).

Это обеспечивает синхронизацию всех участников с точностью до половины RTT сети.

### 11.8. Реакции

Участники могут реагировать на контент во время воспроизведения:

- **Реакции эмодзи**: Пакет `WatchReaction` (тип 30) с `Type = Emoji`, содержащий строку эмодзи и позицию в медиа в момент реакции.
- **Голосовые комментарии**: Пакет `WatchReaction` с `Type = VoiceComment`, содержащий аудиоданные в кодировке Opus (максимум 10 секунд). Голосовые данные включаются в поле `VoiceData` реакции.

Реакции рассылаются всем участникам сессии. Они привязаны к позиции в медиа, что позволяет отображать их синхронно при воспроизведении.

### 11.9. ChipIn — Групповое приобретение контента

ChipIn позволяет участникам группы объединять средства (в ZAR, расчёт через кошельки SDPKT посредством LedgerAPI) для совместного приобретения контента для группового просмотра.

**Автомат состояний:**
```
  Collecting ──► Funded ──► Purchasing ──► Acquired
       │                        │
       └── (timeout) ──► Failed/Refunded
```

Состояния: `Collecting(0)`, `Funded(1)`, `Purchasing(2)`, `Acquired(3)`, `Failed(4)`, `Refunded(5)`.

**Процесс:**
1. Инициатор создаёт `ChipInPool` с целевой суммой и описанием контента.
2. Участники вносят суммы через транзакции кошелька SDPKT.
3. При `CollectedAmount >= TargetAmount` состояние переходит в `Funded`.
4. Система приобретает контент (например, инициирует загрузку BitTorrent).
5. Когда контент доступен, состояние переходит в `Acquired` и может начаться совместный просмотр.

Каждый взнос записывается с идентификатором транзакции SDPKT для аудиторского следа.

### 11.10. Модель шифрования

| Режим | Шифрование | Распределение ключей |
|-------|------------|---------------------|
| Sync-команды просмотра | Ключ канала/беседы | Существующая сессия Signal Protocol |
| Фрагменты контента (StreamFromHost) | Ключ контента на манифест | Распределяется через Signal Protocol |
| Части BitTorrent | Повторное шифрование при приёме | Шлюз загружает открытый текст из роя, шифрует для mesh |
| Реакции просмотра | Ключ сессии | Производится из ключа беседы |

### 11.11. Флаги функций

Все функции видео и совместного просмотра защищены флагами функций (все отключены по умолчанию):

| Флаг | Родитель | Описание |
|------|----------|----------|
| AETHERNET_VIDEO_CALL | AETHERNET_VOICE | P2P и групповые видеозвонки |
| AETHERNET_VIDEO_GROUP | AETHERNET_VIDEO_CALL | Многосторонние видеосессии |
| AETHERNET_SCREEN_SHARE | AETHERNET_VIDEO_CALL | Демонстрация экрана в видеозвонках |
| AETHERNET_WATCH_TOGETHER | AETHERNET_CONTENT_P2P | Синхронизированное воспроизведение медиа |
| AETHERNET_WATCH_REACTIONS | AETHERNET_WATCH_TOGETHER | Реакции эмодзи и голосовые реакции |
| AETHERNET_TORRENT_INGEST | AETHERNET_CONTENT_P2P | Принятие файлов BitTorrent для распространения через mesh |

Флаги функций имеют родительские зависимости: дочерний флаг может быть включён только при включённом родительском. Это обеспечивает поэтапное развёртывание.

## 12. Уровень безопасности и конфиденциальности

> Добавлено в 2.3.0. Эталонная реализация: `src/AetherNet.Security/Backup/` (фраза восстановления), `src/AetherNet.Security/Privacy/` (защита от BLE-отслеживания, экстренное стирание) и `src/AetherNet.Security/Sync/` (многоустройственная синхронизация). Межъязыковые байтовые векторы: `fixtures/bip39/`, `fixtures/bleprivacy/`, `fixtures/panicwipe/`, `fixtures/sync/`.

Этот уровень является дополнительным и независимым от набора пакетов из §2. Только **многоустройственная синхронизация** (§12.1–12.2) и **схема адресов защиты от BLE-отслеживания** (§12.3) имеют байтовые / эфирные форматы; **резервное копирование по фразе восстановления** (§12.4) и **экстренное стирание** (§12.5) являются исключительно локальными и описаны здесь для полноты. Все они реализованы байт-в-байт идентично во всех восьми языках, за единственным исключением подписи Ed25519, отмеченным в §12.1.

### 12.1. DeviceLink (сопряжение устройств)

`DeviceLink` — это подписанное Ed25519 утверждение о том, что открытый ключ устройства принадлежит некоторой личности; оно используется для сопряжения собственных устройств пользователя с целью многоустройственной синхронизации. **Подписываемое тело** имеет вид:

| Смещение | Поле | Тип | Размер | Примечания |
|----------|------|-----|--------|------------|
| 0 | format_version | uint8 | 1 | `0x01`; при чтении отклонять любое другое значение |
| 1 | device_id_len | uint16, little-endian | 2 | Длина `device_id` в байтах UTF-8 |
| 3 | device_id | UTF-8 bytes | N | идентификатор связываемого устройства |
| 3+N | device_public_key | bytes | 32 | открытый ключ Ed25519 связываемого устройства |
| 35+N | issued_at_ms | int64, little-endian | 8 | Миллисекунды Unix epoch |

Сериализованный `DeviceLink` — это подписываемое тело, за которым следует **64-байтная подпись Ed25519** над этим телом, вычисленная закрытым ключом *личности*. Проверка пересчитывает тело и сверяет подпись с открытым ключом личности.

> **Исключение по байтовой идентичности подписи.** Подписываемое тело и результат проверки идентичны во всех восьми языках, а 64 **байта** подписи байт-в-байт идентичны в семи из них. CryptoKit от Apple рандомизирует подписи Ed25519 («hedged»-подпись из RFC 8032 §8), поэтому подпись на Swift отличается при каждом вызове, оставаясь при этом действительной и проверяемой между языками. Совместимость ДОЛЖНА опираться на *проверку*, а не на сравнение байтов подписи.

### 12.2. SyncRecord (конверт синхронизации «последняя запись побеждает»)

`SyncRecord` — это одно реплицируемое изменение собственного многоустройственного состояния пользователя, согласуемое по принципу «последняя запись побеждает». Записи передаются зашифрованными сквозным шифрованием внутри существующего пути DTN/mesh (`encrypted_payload` — это непрозрачный шифртекст) — они **не** являются новым типом `MeshPacket`.

| Смещение | Поле | Тип | Размер | Примечания |
|----------|------|-----|--------|------------|
| 0 | format_version | uint8 | 1 | `0x01` |
| 1 | record_id | UUID, RFC 4122 big-endian | 16 | та же big-endian-конвенция, что и в §2.1 |
| 17 | op | uint8 | 1 | `0`=Upsert, `1`=Delete, `2`=Read; отклонять > 2 |
| 18 | logical_clock | int64, little-endian | 8 | монотонный счётчик на устройство |
| 26 | created_at_ms | int64, little-endian | 8 | Миллисекунды Unix epoch |
| 34 | device_id_len | uint16, little-endian | 2 | Длина в байтах UTF-8 |
| 36 | device_id | UTF-8 bytes | N | устройство-источник |
| 36+N | item_id_len | uint16, little-endian | 2 | Длина в байтах UTF-8 |
| 38+N | item_id | UTF-8 bytes | M | синхронизируемый логический ключ |
| 38+N+M | payload_len | int32, little-endian | 4 | длина шифртекста; отклонять отрицательные значения |
| 42+N+M | encrypted_payload | bytes | payload_len | непрозрачный сквозной шифртекст |

**Согласование (последняя запись побеждает).** Между двумя записями для одного и того же `item_id` победитель выбирается сравнением по порядку, пока одно из значений не окажется различным: `created_at_ms`, затем `logical_clock`, затем `device_id` (порядковое побайтовое сравнение), затем `record_id` (побайтовое big-endian-сравнение). Порядок является полным и детерминированным, поэтому каждое устройство сходится к одному и тому же победителю независимо от порядка поступления.

### 12.3. Защита от BLE-отслеживания

Две деривации позволяют устройству вести оповещение, не будучи отслеживаемым пассивным сканером. Обе являются чистыми функциями, зафиксированными в `fixtures/bleprivacy/`; их передача в эфир — задача хостового BLE-стека.

- **Ротируемый Service UUID.** `window = floor(unix_time_seconds / 900)` (15-минутная эпоха). Анонсируемый 128-битный Service UUID — это первые 16 байт от `HMAC-SHA256(ble_rotation_key, LE_int64(window))`. Сканер, журналирующий UUID, не может связать два окна без ключа ротации.
- **Разрешимый приватный адрес (RPA).** Согласно функции Bluetooth `ah`: `hash = ah(IRK, prand)`, где `ah` — это AES-128 над 24-битным `prand` (дополненным до 128 бит), из которого берутся младшие 24 бита. 48-битный адрес равен `hash(24) || prand(24)`, при этом два старших бита `prand` устанавливаются в `0b01`, чтобы пометить его как разрешимый. Узел, обладающий IRK, разрешает адрес, пересчитывая `ah` и сравнивая хеш.

### 12.4. Резервное копирование по фразе восстановления (локально)

Личность — это пара ключей Ed25519, чьё 32-байтное закрытое зерно (256 бит) кодируется в виде мнемоники **BIP-39 из 24 слов** по официальному английскому списку слов, со стандартной контрольной суммой SHA-256 (слово с опечаткой не проходит контрольную сумму и отклоняется, а не даёт молча другую личность). Это стандартный BIP-39 — проверенный по официальным тестовым векторам Trezor и воспроизведённый байт-в-байт во всех восьми языках — так что фраза восстанавливает личность на любом устройстве без сервера или хранителя. Формата передачи нет; фраза никогда не попадает в сеть.

### 12.5. Экстренное стирание (локально)

Под принуждением **PIN принуждения** — сравниваемый с сохранённым `SHA-256(pin)` за постоянное время — запускает безопасное стирание всего ключевого материала личности: каждый буфер перезаписывается случайными байтами, а затем обнуляется, по фиксированному манифесту имён ключей личности (пара ключей личности, соль устройства, DRK, а также ключ ротации BLE / IRK из §12.3). Формата передачи нет; операция полностью локальна для устройства.

## Приложение B: Глоссарий

| Термин | Определение |
|--------|-------------|
| **UHID** | Universal Hardware Identifier. Уникальная строка, идентифицирующая mesh-узел, производная от идентичности устройства и криптографических ключей. |
| **RREQ** | Route Request. Широковещательный пакет, используемый для обнаружения пути к узлу назначения. |
| **RREP** | Route Reply. Unicast-пакет, отправляемый обратно по обратному маршруту, установленному RREQ. |
| **IRK** | Identity Resolving Key. 128-битный ключ, используемый для генерации и разрешения BLE Resolvable Private Addresses. |
| **RPA** | Resolvable Private Address. 6-байтовый BLE-адрес, периодически ротирующийся, но доступный для разрешения узлами, обладающими IRK отправителя. |
| **X3DH** | Extended Triple Diffie-Hellman. Протокол согласования ключей, обеспечивающий асинхронное установление сессии. |
| **DTN** | Delay-Tolerant Networking. Парадигма store-and-forward для сред с нестабильным соединением. |
| **Gateway** | Mesh-узел с интернет-подключением, обеспечивающий мост между mesh-трафиком и IP-сервисами. |
| **HKDF** | HMAC-based Key Derivation Function. Используется для вывода множества ключей из одного общего секрета. |
| **Pre-key bundle** | Опубликованный набор ключей, позволяющий отправителю установить зашифрованную сессию без присутствия получателя онлайн. |
| **SFU** | Selective Forwarding Unit. Узел-ретранслятор, получающий один видеопоток от каждого отправителя и распределяющий его всем остальным участникам, снижая нагрузку на исходящую полосу каждого узла. |
| **ChipIn** | Механизм группового финансирования, позволяющий участникам объединять средства SDPKT для совместного приобретения контента для группового просмотра. |
| **NAL** | Network Abstraction Layer. Формат инкапсуляции, используемый кодеками H.264 и H.265 для пакетизации видеофреймов. |
