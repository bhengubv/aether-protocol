# Aether プロトコル — 脅威モデル

**HEAD `b8b3d22`（2026-05-06）に対してレビュー済み。** このドキュメントは、`aether-protocol` の暗号プロトコル層が何を防御するか、明示的にスコープ外となるもの、およびセキュリティ主張が依拠する前提条件を説明します。意図的に正直な記述となっています: このドキュメントを読んだ攻撃者は、プロトコルが防御 **しない** すべての攻撃を列挙できるべきであり、README のマーケティング文言に惑わされるべきではありません。

関連ドキュメントは [`PROTOCOL_SPEC.md`](PROTOCOL_SPEC.md) §7（セキュリティモデル）です。両者が食い違う場合は、`src/AetherNet.Security/` の実装が権威を持ちます。

---

## 1. スコープ

### `aether-protocol` が提供するもの

Signal プロトコルスタイルのエンドツーエンド暗号化メッセージングライブラリと、メッシュネットワーキングプリミティブ（AODV スタイルのルーティング + DTN ストアアンドフォワード + SOS フラッド）です。コアのセキュリティ保証は以下のとおりです:

1. **機密性** — メッセージ本体は、ダブルラチェット（Signal §5）から導出されたメッセージごとの鍵で AES-256-GCM 暗号化されています。
2. **真正性** — すべての `MeshPacket` は、標準的な署名対象データバッファ（PROTOCOL_SPEC §2.4）に対する Ed25519 署名を持ちます。
3. **リプレイ防止** — パケットは、5 分間の鮮度ウィンドウ内で `(SourceUhid, PacketNonce)` が重複した場合に破棄されます。
4. **フォワードセクレシーとポストコンプロマイズセクレシー** — ダブルラチェットは往復ごとの DH 公開鍵変更時に再鍵交換を行います; セッション鍵が侵害されても、過去および将来のメッセージは復元できません。

### `aether-protocol` が提供しないもの

- **トランスポート層セキュリティの代替ではありません。** クライアント→サーバー間には TLS を使用してください。Aether の E2EE はピアツーピアのメッシュトラフィック向けです; パケットがメッシュを離れて中央集権型バックエンドに入った瞬間、そのバックエンドのトランスポートセキュリティはホストの責任です。
- **鍵管理システムではありません。** ホストは `IPreKeyStore`（または任意の `IKeyValueStore` バックアップアダプター）を介して、アイデンティティおよびプリキーマテリアルの永続ストレージを提供します。ハードウェアキーストアの統合、TPM アテステーション、鍵エスクロー回復、保存時の暗号化はすべてホストの責任です。
- **認証システムではありません。** Aether は「アイデンティティキー X を保持している者がこのパケットを送信した」と認証します。アイデンティティキー X を「人間の Alice」にマッピングするのは、ホストの UX 責任です（セーフティナンバー比較、帯域外フィンガープリント交換、事前信頼チェーン）。
- **プライバシーネットワークではありません。** ワイヤーはメッセージタイプ、パケット長、送信元 UHID、宛先 UHID、ホップ数、タイミングを公開します。Tor ではありません。

## 2. 防御対象の攻撃

### 2.1. 通信経路上の盗聴

すべてのペイロードは、ダブルラチェットの対称チェーン（Signal §5.1、`0x01`/`0x02` ドメイン分離付き HMAC-SHA256）から導出されたメッセージごとの鍵で AES-256-GCM 暗号化されています。Alice と Bob の間のすべてのパケットを傍受した攻撃者も、セッション鍵の 1 つなしには何も復元できません。

`tests/AetherNet.Security.Tests/SignalProtocolEncryptionTests.cs` および クロス言語フィクスチャ `fixtures/signal/expected/ratchet_step_basic.json` ベクターによって検証されています。

### 2.2. メッセージ偽造

すべての Wave-2 パケットは、標準的な `BuildSignableData(packet)` バッファ（`src/AetherNet.Security/Services/PacketSigningService.cs`、PROTOCOL_SPEC §2.4）に対する Ed25519 署名を持ちます。偽造されたパケットは検証に失敗し、送信元のアイデンティティ公開鍵を知っているすべてのホップで破棄されます。ルートリプライパケット（RREP）は主張する宛先によって署名されます — 中間ノードは宛先の Ed25519 秘密鍵を保持していないため、宛先になりすますことができません。

### 2.3. リプレイ攻撃

`PacketSigningService.VerifyPacketAsync`:

- `TimestampMs` がローカル UTC から 5 分以上ずれているパケットを拒否します（`FreshnessWindowMs = 5 * 60 * 1000`）。
- `(SourceUhid, PacketNonce)` をキーとして 5 分間の TTL を持つインメモリ重複除去マップを維持します。重複除去キーは、コミット `5bd52a9` で `nonce` 単体から `(source, nonce)` に変更されました。これにより 2 つの障害モードが修正されています: 正規のトラフィックをドロップするクロスセンダーのノンス衝突と、受信者に対してノンスを植え付けて正規の送信者の最初のパケットをブロックする事前登録攻撃です。

カウンター: `aethernet.nonces.replayed`、`aethernet.timestamps.stale`。

### 2.4. フォワードセクレシー（過去の鍵侵害）

ダブルラチェットは、すべての DH ローテーションステップで新しい送信チェーン鍵を導出します（KDF_RK、`salt = current_root_key`、`info = "aether-ratchet-rk-v1"` で HKDF-SHA256 を使用し、64 バイトブロックを新しいルートキーとチェーンキーに 32+32 に分割 — `src/AetherNet.Security/Services/SignalProtocolService.cs`）。現在のセッション状態を侵害した攻撃者は、過去のメッセージを復号できません: 各過去のメッセージ鍵は導出され、次のラチェットステップの前にゼロ化されていました（`CryptographicOperations.ZeroMemory`）。

### 2.5. ポストコンプロマイズセキュリティ（将来の鍵回復）

受信側が受信メッセージの新しい `SenderEphemeralKeyX25519` を観察すると、受信時に DH ラチェットステップを実行します（Signal §5.2）。攻撃者のキャッシュされたセッション状態は、次の往復で古くなります; セッションをスナップショットして立ち去った攻撃者は、正規の当事者が 1 ラウンド交換した後はメッセージを復号できなくなります。

受信時の DH ローテーションステップはすべての 8 言語にわたって実装されました — コミット一覧は `OPEN_ISSUES.md` 項目 2 を参照してください。

### 2.6. 1 回限りのプリキーのリプレイ

各ワンタイムプリキー（OPK）はちょうど 1 回だけ消費されます。C# リファレンスは、FIFO 発行、すべてのバンドル生成時の遅延補充、ロック保護されたシングルショット消費（`SignalProtocolService.TopUpOpkPoolNoLock`、`tests/AetherNet.Core.Tests/PreKeyPoolTests.cs` によって検証済み）を持つ 100-OPK プールを提供します。OPK は X3DH 中にレスポンダーが消費した瞬間に削除されゼロ化されます。そのため、同じ OPK ID を再使用するリプレイされたプリキーメッセージはセッションを確立できません。

**解決済み（全 8 言語）。** セッション対応の他の 7 言語も、いまや同じ 100-OPK プールを、FIFO の
一度きり発行、遅延補充、ロック保護されたシングルショット消費とともに提供しており、これにより以前の
セッションごと単一 OPK のコンカレンシーハザードを解消しました: Rust
（`rust/src/security/signal_protocol.rs` — `DEFAULT_OPK_POOL_SIZE = 100`、
`available_opk_ids: VecDeque<i32>`、`top_up_opk_pool`）、Go
（`go/security/signal_protocol.go` — `DefaultOpkPoolSize = 100`、
`topUpOpkPoolLocked`）、Python
（`python/aethernet/security/signal_protocol.py` —
`DEFAULT_OPK_POOL_SIZE = 100`、`available_opk_ids: Deque`、
`_top_up_opk_pool_locked`）、TypeScript
（`typescript/src/security/PreKeyStore.ts` — 一度きり消費の FIFO プール、
`typescript/tests/opk_pool.test.ts`）、Kotlin
（`kotlin/src/main/kotlin/aethernet/security/SignalProtocol.kt` —
`DEFAULT_OPK_POOL_SIZE = 100`、`ArrayDeque<Int>`、`topUpOpkPoolNoLock`）、
Swift（`swift/Sources/AetherNetProtocol/Security/SignalProtocol.swift` —
`defaultOpkPoolSize = 100`、`removeFirst()` FIFO、`topUpOpkPool`）、および C
（`c/src/signal_protocol.c` — `AETHERNET_SIGNAL_OPK_POOL_SIZE = 100`、プールは
`aethernet_signal_service_init` で 1..100 にシードされ、最初の未消費分を発行、レスポンダの
X3DH で OPK をゼロ化し `consumed` にマーク）。

### 2.7. クロス言語のワイヤードリフト

すべての実装は `fixtures/` 以下のフィクスチャコーパスに対してバイト同一の出力を生成しなければなりません:

- `fixtures/expected/*.bin` — 10 のパケットシリアライゼーションフィクスチャ、CI での 122 のクロス言語バイト等価アサーション。
- `fixtures/signal/expected/x3dh_basic.json` — X3DH 計算（4 つの X25519 DH、`info = "aether-x3dh-root-v1"` での HKDF-SHA256 ルート）。
- `fixtures/signal/expected/ratchet_step_basic.json`、`ratchet_step_three_iterations.json` — 対称ラチェット KDF。
- `fixtures/signal/expected/kdf_rk_basic.json` — DH ラチェットステップ。

いずれかの言語の HKDF info 文字列、バイトオーダー、またはパディングのドリフトは、その `SignalFixtureTests` ビルドを失敗させます。ワイヤー互換の相互運用性はビルド時の不変条件であり、ランタイムの希望ではありません。

### 2.8. 静的-静的 DH 侵害（以前の壊れた X3DH）

2026-05-05 以前、C# の `KEY_EXCHANGE` 実装は両方の DH 演算にローカルノードのアイデンティティキーを使用していました — これは X3DH のエフェメラルキーフォワードセクレシー特性を壊す静的-静的の崩壊でした。コミット `07a93f5` によって修正されました: 実際の X3DH は現在、セッションごとの新しいエフェメラルキーで標準的な 4 つの DH `DH(IK_A,SPK_B) || DH(EK_A,IK_B) || DH(EK_A,SPK_B) || DH(EK_A,OPK_B)` を実行します。`OPEN_ISSUES.md` §1 を参照してください。

### 2.9. ルーティングループとブロードキャストストーム

`RoutingService` は `(originUhid, broadcastId)` で RREQ パケットを有界キャッシュ（デフォルト 10,000 エントリ; `ProtocolConstants.RouteRequestDedupCacheSize`）内で重複除去します。TTL はすべてのホップでデクリメントされ、`Ttl == 0` のパケットは破棄されます。SOS ブロードキャストはオリジンごとに 1 時間あたり 3 回に制限されており、自己オリジン抑制によって、ノードが自分自身の SOS を再ブロードキャストするのを防ぎます。

### 2.10. OPK プール枯渇によるサービス妨害

OPK プールは有界です（`OpkPoolSize`、デフォルト 100）。利用可能な OPK が `SignalOptionsBag.MinAvailableOpks`（デフォルト 10）を下回ると、Signal ヘルスチェックが `Unhealthy` を発行します。ホストは `aether-signal` ヘルスステータスにアラートを接続します。バンドルをフェッチして OPK を枯渇させようとした攻撃者は、設定されたプールサイズを超えることができません; レスポンダーの X3DH は既に発行済みのバンドルに対して引き続き機能し、次のバンドル生成で補充が実行されると回復します。

### 2.11. 受動的な BLE デバイストラッキング

安定した BLE MAC または Service UUID をログに記録する受動スキャナーは、デバイスを時間と場所をまたいで追跡できます。`BlePrivacy`（`src/AetherNet.Security/Privacy/BlePrivacy.cs`）は識別子リンク付けのベクターを塞ぎます: アドバタイズされる Service UUID は 15 分ごとに `HMAC-SHA256(rotation_key, window)`（PROTOCOL_SPEC §12.3）として再導出され、ピアは固定の MAC ではなく解決可能プライベートアドレス（IRK + `ah`）でアドレス指定されます。ローテーションキーまたは IRK なしでは、2 つのアドバタイズメントをリンク付けできません。`fixtures/bleprivacy/` にピン留めされています。

**残存リスク。** これは BLE 識別子のベクターのみを塞ぐものです — Aether をプライバシーネットワークにするものでは **ありません**（§1）。パケットがメッシュ上に乗ってしまえば、平文の `MeshPacket` ヘッダーは依然として送信元/宛先 UHID、タイプ、長さ、タイミングを公開し（トラフィック解析はスコープ外のまま、§3.3）、RF 層のフィンガープリンティングは未対応です。ローテーションする識別子を電波上に発信するのはホストの BLE スタックの役割です — ライブラリはそれらを導出するだけです。

### 2.12. 強要による鍵の開示（強制）

物理的に所持し、ユーザーにロック解除を強要する敵対者。`PanicWipe`（`src/AetherNet.Security/Privacy/PanicWipe.cs`）は **強制 PIN** を受け付けます — これは保存された `SHA-256(pin)` に対して定数時間で照合され（早期終了によるタイミングリークなし）、鍵名マニフェスト全体にわたってすべてのアイデンティティキーを安全に消去（ランダムで上書きしてからゼロ化）するため、引き渡されたデバイスは使用可能なアイデンティティを保持しません。`fixtures/panicwipe/` にピン留めされています。

**残存リスク。** ベストエフォートであり、明示的に境界があります: ワイプの *前* にキャプチャされたフォレンジックイメージ、鍵バイトの以前のコピーを保持するフラッシュのウェアレベリング、*本物の* PIN を強要する敵対者、またはメッセージが既に読まれた後の強要に対しては防御 **しません**。定数時間比較は PIN 推測のタイミングを軽減しますが、完全なサイドチャネル敵対者を軽減するものではありません（§3.2）。

### 2.13. 唯一のデバイスの喪失（回復）

攻撃者ではなく、アイデンティティの唯一のコピーを失うという可用性の障害です。リカバリーフレーズバックアップ（`src/AetherNet.Security/Backup/`）は、32 バイトの Ed25519 アイデンティティシードをチェックサム付きの 24 語の BIP-39 フレーズ（PROTOCOL_SPEC §12.4）としてエンコードし、任意のデバイスでアイデンティティを復元します — サーバーやカストディアンはそれを保持しません。

**残存リスク — 新しい窃取面。** フレーズ **こそが** アイデンティティです: 24 語を読んだ者は誰でもユーザーを完全になりすますことができ、失効の手段はありません。これはデバイス喪失リスクを紙の秘密のリスクと引き換えにします。ライブラリはフレーズのエンコード/デコードとチェックサム計算を行います; 安全な表示、保管、およびオプションの BIP-39 パスフレーズはホストの責任です。

### 2.14. マルチデバイス同期への不正デバイスの注入

自分が制御するデバイスを被害者の同期セットに挿入しようとする、または同期レコードを偽造しようとする攻撃者。`DeviceLink`（`src/AetherNet.Security/Sync/`）は **アイデンティティキーによって Ed25519 署名されています**（PROTOCOL_SPEC §12.1）。そのため、新しいデバイスを認可できるのはアイデンティティ保持者のみです — 署名なし、または誤った鍵によるリンクは検証に失敗します。`SyncRecord` ペイロードは DTN/メッシュパスの内部を E2E 暗号化されて移動するため、リレーはそれらを運びますが読み取ることはできません。`fixtures/sync/` にピン留めされています。

**残存リスク。** これは *リンク付け* を認証するものであり、リンクされたデバイスのその後の挙動を認証するものではありません: 正当にリンクされ、*その後* に侵害されたデバイスは、同期されたすべての状態を見ることができます — 同期にはレコードごとのフォワードセクレシーがありません。リコンシリエーションは `(created_at_ms, logical_clock, device_id, record_id)` に対する最終書き込み優先であるため、クロックがずれたリンク済みデバイスは、どのレコードが勝つかにバイアスをかけることができます; クロックの完全性はホストの懸念事項です。署名バイトのパリティは PROTOCOL_SPEC §12.1 に記載された Swift/CryptoKit の例外を伴います。

## 3. スコープ外

これらは、プロトコルが防御 **しない** 実際の攻撃です。一部は将来のリリースで理論上は軽減可能ですが、他は根本的にホストの懸念事項です。

### 3.1. エンドポイントの侵害

攻撃者が Alice のデバイスで root を取得した場合、メモリから彼女のアイデンティティキーのプライベートバイトを読み取り、彼女が保持するすべてのセッションを復号できます。プロトコルはデバイスのプロセスメモリが信頼されていることを前提とします。軽減策（プラットフォームキーストア、SGX、ハードウェアバックドキーストア）は明示的にホストの責任です — セクション 4 を参照してください。

### 3.2. サイドチャネル攻撃

リファレンス実装はラチェット公開鍵比較に `CryptographicOperations.FixedTimeEquals`（`SignalProtocolService.ConstantTimeEquals`）を使用していますが、以下に対しては特に対策されていません:

- AES-GCM のタイミングサイドチャネル（.NET BCL の `AesGcm` は AES-NI 対応 CPU でハードウェアアクセラレートされています; ソフトウェアフォールバックのタイミングは監査されていません）。
- 電力解析サイドチャネル（純粋ソフトウェア — ハードウェア対策なし）。
- 鍵導出パス上のキャッシュタイミング（BCL 経由の HKDF-SHA256）。

盗まれたロック解除されたデバイスに対する国家レベルの研究室による攻撃は可能です。

### 3.3. トラフィック解析

ワイヤー形式は以下を公開します:

- パケットの **タイプ**（オフセット 1 の 1 バイト — RREQ vs Data vs SOS は平文）。
- パケットの **長さ**（ペイロードはパディングされていません）。
- **送信元および宛先 UHID**（UTF-8、平文）。
- **タイムスタンプ**、**TTL**、**優先度**。

パディング、カバートラフィック、オニオンルーティングは実装されていません。BLE / Wi-Fi トラフィックを受動的に観察できる敵対者は、コンテンツを読めなくても、連絡先グラフとすべての会話のタイミングプロファイルを構築できます。これは既知の制限です; 軽減策にはワイヤー形式の変更が必要であり、現在のロードマップには含まれていません。

### 3.4. 量子コンピューター攻撃

X25519（RFC 7748）と Ed25519（RFC 8032）はどちらも、Shor のアルゴリズムを実行する十分に大きな量子コンピューターで解読されます。このプロトコルは **ポスト量子ではありません**。ハイブリッド Kyber + X25519 / Dilithium + Ed25519 スキームへの将来の移行は既知の懸念事項ですが、スケジュールされていません。「今収集して後で復号する」を狙う敵対者によって今日記録された既存の暗号文は、関連する時間軸内に CRQC が登場した場合にリスクにさらされます。

### 3.5. 大規模グループメッセージング

`AetherNet.Security` は `IGroupKeyProvider` シームを提供していますが、完全な Signal Sender Keys プロトコル（Signal が使用する非同期グループメッセージング構成）は HEAD 時点では実装 **されていません**。今日グループメッセージングが必要なホストは、N 個のペアワイズセッションにフォールバックします — これは機能しますが、グループ送信ごとに O(N) のコストがかかります。PROTOCOL_SPEC §7 は単一受信者の脅威のみをカバーしています。

### 3.6. 最初の接触でのアイデンティティ検証（TOFU）

Aether は「アイデンティティキー X を保持しているピアがこれに署名した」と認証します。「アイデンティティキー X が実際にユーザーが話していると期待している人間の Alice のものである」とは認証 **しません**。最初の接触時、最初のバンドル交換中にネットワークを制御している積極的な中間者攻撃者は、自分自身のアイデンティティキーに置き換え、自分自身のバンドルに署名し、両方向でトラフィックを透過的にプロキシできます。

これは標準的な Signal の「Trust On First Use」の弱点です。標準的な軽減策は、帯域外での（対面で、別のチャネルを通じて、事前共有された検証画面で）セーフティナンバー / フィンガープリント比較です。このプロトコルは現在、セーフティナンバー導出のための公開 API サーフェスを公開していません; ギャップとして追跡中（まだ `OPEN_ISSUES.md` には記載なし）— ホスト UX はデフォルトで検証済みであるかのような表示をすべきではありません。

### 3.7. 基礎となるトランスポートに対するネットワーク層攻撃

信号妨害（BLE、Wi-Fi、NearLink）、RF 層のサービス妨害、およびトランスポートのペアリング/ボンディングフローに対する攻撃はスコープ外です。トランスポート（`ITransportService`）は不透明なバイトパイプとして扱われます。スペクトルを占有するジャマーは Aether が何も配信するのを止めます。

### 3.8. 重複除去ウィンドウを超えたルーティング攻撃

まだ信頼性スコアを蓄積していない短命ノードによるシビル攻撃、信頼性ヒューリスティックをトリガーしない日和見的なリレードロップ、レート制限内にとどまるリソース枯渇攻撃は特に対策されていません。信頼性スコア（PROTOCOL_SPEC §3.5）は実績のある悪いノードを優先度下げしますが、完全な Byzantine 耐性ルーティングプロトコルではありません。

## 4. セキュリティ主張が成立するための前提条件

セクション 2 の防御は以下の不変条件を前提としています。これらのいずれか 1 つが破れると、対応するセキュリティ特性が失われます。

1. **アイデンティティキーの永続性。** ホストは長期 Ed25519 + X25519 アイデンティティキーペアを永続的かつ安全に保存します（例: `EncryptedKeyValueStore` でラップされた `FileSystemKeyValueStore` に対する `IPreKeyStore`、またはプラットフォームキーストア）。アイデンティティキーの喪失はアカウントの完全な侵害を意味します; 秘密鍵の保持者は元のピアとして何でも署名できます。

2. **CSPRNG の正確性。** ターゲットプラットフォームの `RandomNumberGenerator.GetBytes` と `RandomNumberGenerator.GetInt32` が暗号論的に安全な出力を生成します。プロトコル全体 — エフェメラルキー、AES-GCM ノンス、パケットノンス、OPK ID — はこれに依存しています。BCL ランダムソースが低下しているプラットフォーム（一部の組み込みターゲット、壊れた Linux エントロピープール）では、信頼ツリー全体が崩壊します。

3. **システムクロックが UTC ±5 分以内。** リプレイ防止はタイムスタンプウィンドウ付きです。クロックが大きくずれたデバイスは、すべてのパケットを拒否するか（クロックが古すぎる）、無期限にリプレイを受け入れます（クロックが新しすぎる）。ホストはアプリ起動時に信頼できる時刻ソースに対するサニティチェックを実施するべきです（SHOULD）。

4. **原子的な OPK 消費。** `IPreKeyStore` バックの `ConsumeOneTimePreKeyAsync(id)` が同じ ID に対するレスポンダー X3DH 演算と並行して実行される場合、消費は原子的に成功または失敗しなければなりません。C# リファレンスプールは `_preKeyLock` 下で消費をシリアライズします; 非トランザクショナルバックエンド（例: 読み取り-変更-書き込みのナイーブなファイルストア）上のホスト提供ストアは、同じ OPK が 2 回消費されることを許可してしまい、特性 2.6 を壊す可能性があります。`KeyValuePreKeyStore` は消費に `IKeyValueStore.RemoveAsync` を直接使用します — 基礎となる KV の削除が原子的であれば原子的です。

5. **最初の接触でのアイデンティティ検証。** ピアのアイデンティティ公開鍵は、最初の交換メッセージの前に帯域外で検証されていました（セーフティナンバー、フィンガープリント、信頼できるディレクトリ）— またはホストが TOFU リスクを受け入れ、次の接触で鍵の変更を検出することに満足しています。これなしでは、§3.6 がオープンな MitM ウィンドウとなります。

6. **ホストのプロセスメモリは敵対者が読み取れない。** §3.1。

## 5. 既知の脆弱性 + 軽減策

### 5.1. 最初の接触での中間者攻撃（TOFU）

**脆弱性:** 最初のバンドル交換中にピアツーピアリンクを制御している積極的な攻撃者は、自分自身のバンドルに置き換えてトラフィックをプロキシできます。
**軽減策:** ホスト UX は、コンタクトを検証済みとして扱う前にセーフティナンバー / 公開鍵フィンガープリント比較フローを公開しなければなりません。セーフティナンバー導出のための公開 API サーフェスはまだ `AetherNet.Security` に含まれていません; ギャップとして追跡中。

### 5.2. 署名済みプリキーのローテーション遅延

**脆弱性:** ホストが `RotateSignedPreKeyAsync` を呼び出すまで、同じ SPK がすべてのバンドルで提供されます。SPK 秘密鍵を学習した攻撃者（例: §3.1 のエンドポイント侵害経由）は、最後のローテーション以降のキャプチャされたすべてのバンドルに対して X3DH を実行できます。
**軽減策:** 毎日 `RotateSignedPreKeyAsync` 呼び出しをスケジュールしてください。デフォルトの `SignedPreKeyRotationOptions` は 3 つの以前の SPK を保持するため、最近ローテーションされた鍵で署名された進行中のメッセージはローテーションウィンドウ中も復号できます。デフォルトのローテーション間隔は 7 日間です — 積極的に標的にされたユーザーに対して実行しているアダプターはこれを短縮すべきです。

### 5.3. 永続化なしのインメモリセッション状態

**脆弱性:** `SignalProtocolService` が `sessionStore` なしで構築された場合、プロセスのクラッシュまたは再起動はすべてのアクティブセッションを失います。フォワードセクレシーは保たれます（失われた鍵は回復できません）が、次のピアからのメッセージは受信チェーンがないため復号に失敗します。
**軽減策:** 本番デプロイには、永続的な `IKeyValueStore` に対して `KeyValueSignalSessionStore` を接続してください。サンプルコンソールデモは明確さのために `InMemoryDtnBundleStore` などを使用しています; 本番ホストはこうすべきではありません。

### 5.4. 圧縮フラグのワイヤーバイト移行ウィンドウ

**脆弱性:** `MessagingService` には、プレーンテキストエンベロープの前に無条件のフラグバイトを追加するオプションの Brotli 圧縮シームがあります。圧縮前のコードを実行しているピアは、フラグバイトをアプリケーションペイロードの最初のバイトとして誤読します。
**軽減策:** すべてのピアが新しいビットを持つまで、アダプターは `MessagingOptions.Compression.Enabled = false` を設定してください。フラグバイトは将来のケイパビリティネゴシエーションハンドシェイクによってゲートされます。`CompressionOptions` の移行ノートを参照してください。

### 5.5. C 言語のギャップ — 解決済み

**かつての脆弱性:** C 実装は X25519 + KDF_RK プリミティブとフィクスチャベリファイアのみを提供し、
完全な `SignalProtocolService` API がありませんでした。
**解決済み。** `c/src/signal_protocol.c` はいまや完全なセッションサービスを実装しています — X3DH
確立（`aethernet_signal_process_pre_key_bundle` での SPK Ed25519 署名検証に続く、標準的な 4 つの DH
`DH(IK_A,SPK_B) || DH(EK_A,IK_B) || DH(EK_A,SPK_B) || DH(EK_A,OPK_B)` と HKDF-SHA256 ルート）、
OPK / SPK ライフサイクル（プールは `aethernet_signal_service_init` で 1..100 にシード、`has_pre_key`
バンドル投影、レスポンダ側で OPK 消費）、および完全な Double-Ratchet 統合
（`dh_ratchet_receive`、`dh_ratchet_send_only`、AES-256-GCM 上の
`aethernet_signal_encrypt` / `aethernet_signal_decrypt`）。2 ノードの E2E ラウンドトリップは
`c/tests/test_signal_session.c` にあります。C ベースのターゲット上のホストは、いまや C サーフェスで
エンドツーエンド暗号化トラフィックを実行できます。

### 5.6. OPK プールは C# のみ — 解決済み

**かつての脆弱性:** FIFO 発行と原子的消費を持つ 100-OPK プール（防御 2.6）は C# のみの機能でした。
他の言語はセッションごとに 1 つの OPK を発行していたため、同時イニシエーター負荷下では、同じバンドル
ソースを競合する 2 つのレスポンダーが同じ OPK を観察し、X3DH がセッション状態の不一致を生成し得ました。
**解決済み（全 8 言語）。** セッション対応のすべての言語が、いまや同じ 100-OPK プールを、FIFO の
一度きり発行、遅延補充、ロック保護されたシングルショット消費とともに提供しています — 言語ごとの
file:symbol の証跡は防御 2.6 に列挙されています。同時イニシエーターのハザードは解消され、バンドル消費の
ホスト側シリアライズは不要です。

### 5.7. C# 以外の言語でのデモ署名

**脆弱性:** 言語ごとのデモプログラム（Go、Python、TS、Rust、Swift、Kotlin、C）は、標準的な `BuildSignableData` バッファではなく、可視化のためにシリアライズされたワイヤーバイト全体に署名します。これらの言語のライブラリコードは正しいです — デモのみがショートカットを取りますが、ポーターには紛らわしいです。
**軽減策:** `OPEN_ISSUES.md` §10 として追跡されています。C# デモのステップ 3 を標準的なフローとして扱ってください。

セクション 3 のスコープ外に該当する問題も歓迎します — 本番環境でユーザーがギャップを発見するよりも、防御していないものを把握しておく方が望ましいです。
