# Aether Protocol — 위협 모델

**HEAD `b8b3d22` (2026-05-06) 기준으로 검토되었습니다.** 이 문서는 `aether-protocol`의
암호화 프로토콜 계층이 방어하는 대상, 명시적으로 범위 밖에 있는 항목, 그리고 보안 주장이
의존하는 가정들을 설명합니다. 의도적으로 솔직하게 작성되었습니다: 이 문서를 읽는 공격자는
프로토콜이 **막지 못하는** 모든 공격을 열거할 수 있어야 하며, README의 마케팅 문구에 의해
오도되어서는 안 됩니다.

동반 문서는 [`PROTOCOL_SPEC.md`](PROTOCOL_SPEC.md) §7 (보안 모델)입니다. 두 문서가
상충하는 경우, `src/AetherNet.Security/`의 구현이 권위를 가집니다.

---

## 1. 범위

### `aether-protocol`이 하는 것

Signal Protocol 방식의 종단 간 암호화 메시징 라이브러리에 메시 네트워킹 기본 요소
(AODV 방식 라우팅 + DTN 저장-전달 + SOS 플러드)를 더한 것입니다. 핵심 보안 보장은
다음과 같습니다:

1. **기밀성** — 메시지 본문은 이중 래칫(Signal §5)에서 파생된 메시지별 키로
   AES-256-GCM 암호화됩니다.
2. **진본성** — 모든 `MeshPacket`은 정규적인 서명 가능 데이터 버퍼에 대한 Ed25519
   서명을 포함합니다 (PROTOCOL_SPEC §2.4).
3. **재전송 공격 보호** — 5분 신선도 창 내에서 `(SourceUhid, PacketNonce)` 중복 시
   패킷이 삭제됩니다.
4. **순방향 및 사후 타협 비밀성** — 이중 래칫은 매 왕복의 DH 공개키 변경 시 재키잉합니다;
   세션 키를 탈취한 공격자는 과거 메시지도 미래 메시지도 복원할 수 없습니다.

### `aether-protocol`이 하지 않는 것

- **전송 계층 보안을 대체하지 않습니다.** 클라이언트→서버에는 TLS를 사용하십시오.
  Aether의 E2EE는 피어-투-피어 메시 트래픽을 위한 것입니다; 패킷이 메시를 벗어나
  중앙화된 백엔드로 나가는 순간, 해당 백엔드의 전송 보안은 호스트의 책임입니다.
- **키 관리 시스템이 아닙니다.** 호스트는 `IPreKeyStore`(또는 `IKeyValueStore` 기반 어댑터)를
  통해 신원 및 사전 키 자료의 영구 저장소를 제공합니다. 하드웨어 키 저장소 통합, TPM 증명,
  키 에스크로 복구, 및 미사용 데이터 암호화는 모두 호스트의 역할입니다.
- **인증 시스템이 아닙니다.** Aether는 "신원 키-X를 보유한 자가 이 패킷을 전송했다"는
  것을 인증합니다. 신원 키-X를 "인간 Alice"에 매핑하는 것은 호스트의 UX 책임입니다
  (안전 번호 비교, 대역 외 지문 교환, 사전 신뢰 체인).
- **프라이버시 네트워크가 아닙니다.** 와이어는 메시지 유형, 패킷 길이, 소스 UHID,
  목적지 UHID, 홉 카운트 및 타이밍을 노출합니다. Tor가 아닙니다.

## 2. 방어되는 공격

### 2.1. 전송 중 도청

모든 페이로드는 이중 래칫의 대칭 체인에서 파생된 메시지별 키로 AES-256-GCM 암호화됩니다
(Signal §5.1, HMAC-SHA256, `0x01`/`0x02` 도메인 분리). Alice와 Bob 사이의 모든 패킷을
캡처한 공격자는 세션 키 중 하나 없이는 아무것도 복원할 수 없습니다.

`tests/AetherNet.Security.Tests/SignalProtocolEncryptionTests.cs` 및 크로스-언어
`fixtures/signal/expected/ratchet_step_basic.json` 벡터로 검증됩니다.

### 2.2. 메시지 위조

모든 Wave-2 패킷은 정규적인 `BuildSignableData(packet)` 버퍼에 대한 Ed25519 서명을 포함합니다
(`src/AetherNet.Security/Services/PacketSigningService.cs`, PROTOCOL_SPEC §2.4). 위조된 패킷은
소스의 신원 공개 키를 아는 모든 홉에서 검증에 실패하여 삭제됩니다. 경로 응답 패킷(RREP)은
주장된 목적지가 서명합니다 — 중간 노드는 목적지의 Ed25519 개인 키를 보유하지 않으므로
목적지를 사칭할 수 없습니다.

### 2.3. 재전송 공격

`PacketSigningService.VerifyPacketAsync`:

- `TimestampMs`가 로컬 UTC에서 5분 이상 차이 나는 패킷을 거부합니다
  (`FreshnessWindowMs = 5 * 60 * 1000`).
- 5분 TTL의 `(SourceUhid, PacketNonce)` 키 기반 인메모리 중복 제거 맵을 유지합니다.
  중복 제거 키는 커밋 `5bd52a9`에서 `nonce` 단독에서 `(source, nonce)`로 변경되어
  두 가지 실패 모드를 수정했습니다: 크로스-발신자 논스 충돌로 인한 정당한 트래픽 삭제,
  그리고 적대자가 수신자에 대해 논스를 심어 정당한 발신자의 첫 번째 패킷을 차단하는
  사전 등록 공격.

카운터: `aethernet.nonces.replayed`, `aethernet.timestamps.stale`.

### 2.4. 순방향 비밀성 (과거 키 타협)

이중 래칫은 모든 DH-로테이션 단계에서 새로운 전송 체인 키를 파생합니다 (KDF_RK,
HKDF-SHA256, `salt = current_root_key`, `info = "aether-ratchet-rk-v1"`, 64바이트 블록을
새로운 루트와 체인 키로 32+32 분할 — `src/AetherNet.Security/Services/SignalProtocolService.cs`).
현재 세션 상태를 탈취한 공격자는 이전 메시지를 복호화할 수 없습니다: 각 이전 메시지 키는
다음 래칫 단계 전에 파생되고 제로화(`CryptographicOperations.ZeroMemory`)되었기 때문입니다.

### 2.5. 사후 타협 보안 (미래 키 복구)

수신 측이 인바운드 메시지에서 새로운 `SenderEphemeralKeyX25519`를 감지하면, 수신 시
DH-래칫 단계를 실행합니다 (Signal §5.2). 공격자의 캐시된 세션 상태는 다음 왕복에서 만료됩니다;
세션을 스냅샷하고 물러난 공격자는 정당한 당사자들이 한 라운드를 교환한 후에는 메시지를
더 이상 복호화할 수 없습니다.

수신 시 DH-로테이션 단계가 8개 언어 전체에 구현되었습니다 — 패밀리 전체 커밋 목록은
`OPEN_ISSUES.md` 항목 2를 참조하십시오.

### 2.6. 일회용 사전 키 재전송

각 일회용 사전 키(OPK)는 정확히 한 번만 사용됩니다. C# 레퍼런스는 FIFO 발급, 모든 번들
생성 시 지연 보충, 그리고 잠금 보호된 단일 소비(`SignalProtocolService.TopUpOpkPoolNoLock`,
`tests/AetherNet.Core.Tests/PreKeyPoolTests.cs`로 검증)가 포함된 100-OPK 풀을 제공합니다.
OPK는 응답자가 X3DH 중에 소비하는 즉시 제거되고 제로화되므로, 동일한 OPK id를 재사용하는
재전송된 사전 키 메시지는 세션을 확립할 수 없습니다.

나머지 7개 언어는 세션당 단일 OPK를 발급합니다 — 순차적인 워크로드에서는 기능적으로
올바르지만 동시 번들 가져오기 시 동시성 위험을 노출합니다. `OPEN_ISSUES.md` §9에서
추적됩니다.

### 2.7. 크로스-언어 와이어 드리프트

모든 구현체는 `fixtures/` 아래의 픽스처 코퍼스에 대해 바이트 단위로 동일한 출력을 생성해야 합니다:

- `fixtures/expected/*.bin` — 10개의 패킷 직렬화 픽스처, CI에서 122개의 크로스-언어 바이트
  동등성 어설션.
- `fixtures/signal/expected/x3dh_basic.json` — X3DH 수학 (4개의 X25519 DH,
  HKDF-SHA256 루트, `info = "aether-x3dh-root-v1"`).
- `fixtures/signal/expected/ratchet_step_basic.json`, `ratchet_step_three_iterations.json`
  — 대칭 래칫 KDF.
- `fixtures/signal/expected/kdf_rk_basic.json` — DH-래칫 단계.

어떤 언어의 HKDF 정보 문자열, 바이트 순서, 또는 패딩의 드리프트도 해당 언어의
`SignalFixtureTests` 빌드를 실패시킵니다. 와이어 호환 상호운용성은 따라서 런타임 희망이
아닌 빌드 타임 불변입니다.

### 2.8. 정적-정적 DH 타협 (이전의 깨진 X3DH)

2026-05-05 이전에, C# `KEY_EXCHANGE` 구현은 두 DH 연산 모두에 로컬 노드의 신원 키를
사용했습니다 — X3DH 임시 키 순방향 비밀성 속성을 깨는 정적-정적 붕괴였습니다.
커밋 `07a93f5`로 수정되었습니다: 실제 X3DH는 이제 세션별 새 임시키와 함께
정규적인 4개의 DH `DH(IK_A,SPK_B) || DH(EK_A,IK_B) || DH(EK_A,SPK_B) || DH(EK_A,OPK_B)`를
수행합니다. `OPEN_ISSUES.md` §1을 참조하십시오.

### 2.9. 라우팅 루프 및 브로드캐스트 폭풍

`RoutingService`는 경계가 있는 캐시(기본값 10,000개 항목; `ProtocolConstants.RouteRequestDedupCacheSize`)에서
`(originUhid, broadcastId)`로 RREQ 패킷을 중복 제거합니다. TTL은 매 홉에서 감소되며
`Ttl == 0`인 패킷은 삭제됩니다. SOS 브로드캐스트는 원점당 시간당 3회로 속도 제한되며,
자기 원점 억제는 노드가 자신의 SOS를 재전송하는 것을 방지합니다.

### 2.10. OPK 풀 고갈을 통한 DoS

OPK 풀은 경계가 있으며(`OpkPoolSize`, 기본값 100) Signal 상태 확인은 가용 OPK가
`SignalOptionsBag.MinAvailableOpks`(기본값 10) 아래로 떨어지면 `Unhealthy`를 발생시킵니다.
호스트는 `aether-signal` 상태에 대한 경고를 연결합니다. 번들을 가져와 OPK를 고갈시키는
공격자는 구성된 풀 크기를 초과할 수 없습니다; 응답자의 X3DH는 이미 발급된 번들에서 계속
작동하며 다음 번들 생성 시 보충이 실행될 때 복구됩니다.

## 3. 범위 밖

이것들은 프로토콜이 **막지 못하는** 실제 공격입니다. 일부는 향후 릴리스에서 이론적으로
완화될 수 있으며, 나머지는 근본적으로 호스트의 관심사입니다.

### 3.1. 엔드포인트 타협

공격자가 Alice의 기기에 루트 권한을 가지고 있으면 메모리에서 그녀의 신원 키 개인 바이트를
읽어 그녀가 보유한 모든 세션을 복호화할 수 있습니다. 프로토콜은 기기의 프로세스 메모리를
신뢰할 수 있다고 가정합니다. 완화 방법(플랫폼 키 저장소, SGX, 하드웨어 지원 키 저장소)은
명시적으로 호스트의 책임입니다 — 섹션 4를 참조하십시오.

### 3.2. 사이드 채널 공격

레퍼런스 구현은 래칫 공개키 비교에 `CryptographicOperations.FixedTimeEquals`
(`SignalProtocolService.ConstantTimeEquals`)를 사용하지만 다음에 대해서는 특별히 강화되지
않았습니다:

- AES-GCM의 타이밍 사이드 채널 (.NET BCL `AesGcm`은 AES-NI 지원 CPU에서 하드웨어
  가속됩니다; 소프트웨어 폴백 타이밍은 감사되지 않았습니다).
- 전력 분석 사이드 채널 (순수 소프트웨어 — 하드웨어 대응책 없음).
- 키 파생 경로의 캐시-타이밍 (BCL을 통한 HKDF-SHA256).

탈취된 잠금 해제 기기에 대한 국가 등급 연구소 공격은 가능합니다.

### 3.3. 트래픽 분석

와이어 형식은 다음을 노출합니다:

- 패킷 **유형** (오프셋 1의 1바이트 — RREQ vs 데이터 vs SOS가 평문으로 표시됨).
- 패킷 **길이** (페이로드는 패딩되지 않음).
- **소스 및 목적지 UHID** (UTF-8, 평문으로 표시됨).
- **타임스탬프**, **TTL**, 및 **우선순위**.

패딩, 커버 트래픽, 양파 라우팅은 구현되지 않았습니다. BLE / Wi-Fi 트래픽을 수동적으로
관찰할 수 있는 적대자는 내용을 읽을 수 없더라도 연락처 그래프와 모든 대화의 타이밍 프로파일을
구축할 수 있습니다. 이는 알려진 한계입니다; 완화를 위해서는 와이어 형식 변경이 필요하며
현재 로드맵에는 없습니다.

### 3.4. 양자 공격

X25519 (RFC 7748)와 Ed25519 (RFC 8032) 모두 Shor 알고리즘을 실행하는 충분히 큰 양자
컴퓨터 아래에서는 깨집니다. 프로토콜은 **포스트-양자가 아닙니다**. 하이브리드
Kyber + X25519 / Dilithium + Ed25519 방식으로의 향후 마이그레이션은 알려진 우려사항이지만
일정이 잡혀 있지 않습니다. 관련 시간 지평 내에 CRQC가 도달하면, 오늘날 "지금 수집, 나중에
복호화" 전략을 가진 적대자가 기록한 기존 암호문은 위험에 처합니다.

### 3.5. 대규모 그룹 메시징

`AetherNet.Security`는 `IGroupKeyProvider` 이음새를 제공하지만, 완전한 Signal 발신자 키
프로토콜(Signal이 사용하는 비동기 그룹 메시징 구조)은 HEAD 기준으로 **구현되지 않았습니다**.
오늘날 그룹 메시징이 필요한 호스트는 N개의 쌍별 세션으로 폴백합니다 — 작동하지만
그룹 전송당 O(N) 비용이 발생합니다. PROTOCOL_SPEC §7은 단일 수신자 위협만 다룹니다.

### 3.6. 첫 접촉 시 신원 확인 (TOFU)

Aether는 "신원 키-X를 보유한 피어가 이것을 서명했다"는 것을 인증합니다. "신원 키-X가
실제로 사용자가 대화하기를 기대하는 인간 Alice에게 속한다"는 것은 인증하지 **않습니다**.
첫 접촉 시, 최초 번들 교환 중에 네트워크를 제어하는 능동적인 중간자는 자신의 신원 키를
대체하고, 자신의 번들에 서명하고, 양방향으로 트래픽을 투명하게 프록시할 수 있습니다.

이는 표준 Signal "첫 사용 시 신뢰(TOFU)" 취약점입니다. 정규적인 완화 방법은 안전 번호 /
지문 비교를 대역 외(직접 대면, 별도 채널, 사전 공유 검증 화면)로 수행하는 것입니다.
프로토콜은 현재 안전 번호 파생을 위한 공개 API 표면을 노출하지 않습니다;
`OPEN_ISSUES.md`에는 아직 없는 gap으로 추적됩니다 — 호스트 UX는 기본적으로 검증된 것처럼
가장해서는 안 됩니다.

### 3.7. 기반 전송에 대한 네트워크 계층 공격

신호 재밍(BLE, Wi-Fi, NearLink), RF 계층 서비스 거부, 및 전송의 페어링/본딩 플로우에 대한
공격은 범위 밖입니다. 전송(`ITransportService`)은 불투명한 바이트 파이프로 취급됩니다.
스펙트럼을 소유한 재머는 Aether가 아무것도 전달하지 못하게 합니다.

### 3.8. 중복 제거 창 이후의 라우팅 공격

신뢰성 점수를 아직 축적하지 않은 단명 노드에 의한 시빌 플러딩, 신뢰성 휴리스틱을 트리거하지
않는 기회적 릴레이 드로핑, 그리고 속도 제한 이하로 유지되는 리소스 고갈 공격은 특별히
완화되지 않습니다. 신뢰성 점수(PROTOCOL_SPEC §3.5)는 입증된 불량 노드의 우선순위를
낮추지만 완전히 비잔틴 내성이 있는 라우팅 프로토콜은 아닙니다.

## 4. 보안 주장이 유지되기 위한 가정

섹션 2의 방어는 다음 불변식에 기반합니다. 이 중 하나라도 깨지면 해당 보안 속성이 손실됩니다.

1. **신원 키 내구성.** 호스트는 장기 Ed25519 + X25519 신원 키 쌍을 영구적이고 안전하게
   저장합니다 (예: `EncryptedKeyValueStore`로 래핑된 `FileSystemKeyValueStore`에 대한
   `IPreKeyStore`를 통해, 또는 플랫폼 키 저장소에 대해). 신원 키 손실 = 전체 계정 타협;
   개인 키를 보유한 자는 원래 피어로서 무엇이든 서명할 수 있습니다.

2. **CSPRNG 정확성.** 대상 플랫폼의 `RandomNumberGenerator.GetBytes` 및
   `RandomNumberGenerator.GetInt32`가 암호학적으로 안전한 출력을 생성합니다. 임시 키,
   AES-GCM 논스, 패킷 논스, OPK id 등 전체 프로토콜이 이에 의존합니다. BCL 랜덤 소스가
   저하된 플랫폼(일부 임베디드 대상, 손상된 Linux 엔트로피 풀)에서는 전체 신뢰 트리가
   무너집니다.

3. **시스템 클럭이 UTC ±5분 이내.** 재전송 공격 보호는 타임스탬프 창으로 작동합니다.
   시계가 크게 틀린 기기는 모든 패킷을 거부하거나(시계가 너무 오래됨) 무기한으로 재전송을
   수락합니다(시계가 너무 새로움). 호스트는 앱 시작 시 신뢰할 수 있는 시간 소스에 대한
   검사를 구현해야 합니다.

4. **원자적 OPK 소비.** `IPreKeyStore` 기반 `ConsumeOneTimePreKeyAsync(id)`가 동일한
   id에 대한 응답자 X3DH 작업과 동시에 실행될 때, 소비는 원자적으로 성공하거나 실패해야
   합니다. 레퍼런스 C# 풀은 `_preKeyLock` 아래에서 소비를 직렬화합니다; 비트랜잭셔널
   백엔드(예: 읽기-수정-쓰기가 있는 단순한 파일 저장소)의 호스트 제공 저장소는 동일한
   OPK가 두 번 소비되어 속성 2.6을 깨는 것을 허용할 수 있습니다. `KeyValuePreKeyStore`는
   소비를 위해 `IKeyValueStore.RemoveAsync`를 직접 사용합니다 — 기반 KV의 제거가 원자적인
   경우 원자적입니다.

5. **첫 접촉 신원 확인.** 피어의 신원 공개 키가 첫 번째 교환된 메시지 전에 대역 외(안전
   번호, 지문, 신뢰할 수 있는 디렉토리)로 검증되었거나 — 호스트가 TOFU 위험을 수용하고
   다음 접촉 시 키 변경을 탐지하는 것에 만족합니다. 이 없이는 §3.6이 열린 MitM 창입니다.

6. **호스트 프로세스 메모리는 적대자가 읽을 수 없습니다.** §3.1.

## 5. 알려진 취약점 + 완화 방법

### 5.1. 첫 접촉 MitM (TOFU)

**취약점:** 최초 번들 교환 중에 피어-투-피어 링크를 제어하는 능동적 공격자가 자신의 번들을
대체하고 트래픽을 프록시할 수 있습니다.
**완화 방법:** 호스트 UX는 연락처를 검증된 것으로 취급하기 전에 안전 번호 / 공개 키 지문
비교 플로우를 노출해야 합니다. 안전 번호 파생을 위한 공개 API 표면은 아직 `AetherNet.Security`에
제공되지 않습니다; gap으로 추적됩니다.

### 5.2. 서명된 사전 키 로테이션 지연

**취약점:** 호스트가 `RotateSignedPreKeyAsync`를 호출하기 전까지, 모든 번들에서 동일한 SPK가
제공됩니다. SPK 개인 키를 알게 된 적대자(예: §3.1 엔드포인트 타협을 통해)는 마지막 로테이션
이후 날짜가 찍힌 모든 캡처된 번들에 대해 X3DH를 실행할 수 있습니다.
**완화 방법:** 일일 `RotateSignedPreKeyAsync` 호출을 예약하십시오. 기본 `SignedPreKeyRotationOptions`는
최근에 로테이션된 키로 서명된 전송 중인 메시지가 로테이션 창 동안 여전히 복호화될 수 있도록
3개의 이전 SPK를 보유합니다. 기본 로테이션 간격은 7일입니다 — 적극적으로 표적이 된 사용자를
대상으로 하는 채택자는 이를 단축해야 합니다.

### 5.3. 영속성 없는 인메모리 세션 상태

**취약점:** `SignalProtocolService`가 `sessionStore` 없이 생성된 경우, 프로세스 충돌 또는
재시작으로 모든 활성 세션이 손실됩니다. 순방향 비밀성은 유지됩니다(손실된 키는 복구될 수
없음) 하지만 피어의 다음 메시지는 수신 체인이 없기 때문에 복호화에 실패합니다.
**완화 방법:** 모든 프로덕션 배포에서 영구적인 `IKeyValueStore`에 대해 `KeyValueSignalSessionStore`를
연결하십시오. 샘플 콘솔 데모는 명확성을 위해 `InMemoryDtnBundleStore` 등을 사용합니다;
프로덕션 호스트는 그렇게 해서는 안 됩니다.

### 5.4. 압축 플래그 와이어 바이트 전환 창

**취약점:** `MessagingService`는 플레인텍스트 봉투 앞에 무조건적인 플래그 바이트를 앞에
추가하는 선택적 Brotli 압축 이음새를 가지고 있습니다. 압축 이전 코드를 실행하는 피어는
플래그 바이트를 애플리케이션 페이로드의 첫 번째 바이트로 잘못 읽습니다.
**완화 방법:** 모든 피어가 새 비트를 갖출 때까지 채택자는 `MessagingOptions.Compression.Enabled =
false`를 설정합니다. 플래그 바이트는 향후 기능 협상 핸드셰이크에 의해 게이팅될 것입니다.
`CompressionOptions`의 마이그레이션 참고사항을 참조하십시오.

### 5.5. C 언어 gap

**취약점:** C 구현은 X25519 + KDF_RK 프리미티브와 픽스처 검증기만 제공합니다. 완전한
`SignalProtocolService` API(X3DH 세션 확립, OPK / SPK 수명 주기, DH-래칫 통합)를 구현하지
**않습니다**. C 기반 마이크로컨트롤러에 Aether를 배포하는 호스트는 종단 간 암호화 트래픽에
현재 C 표면을 사용할 수 없습니다. `OPEN_ISSUES.md` §11에서 추적됩니다.

### 5.6. OPK 풀은 C# 전용

**취약점:** FIFO 발급 및 원자적 소비(방어 2.6)를 갖춘 100-OPK 풀은 C# 레퍼런스 기능입니다.
Go, Python, TypeScript, Rust, Swift, Kotlin 구현은 여전히 세션당 단일 OPK를 발급합니다.
동시 개시자 부하 아래에서, 동일한 번들 소스에 대해 경쟁하는 두 응답자는 동일한 OPK를 모두
관찰할 수 있으며 X3DH는 세션 상태 불일치를 생성할 수 있습니다.
**완화 방법:** 영향받는 언어에서는 호스트 측에서 번들 소비를 직렬화하십시오(피어당 한 번에
한 개시자). `OPEN_ISSUES.md` §9에서 추적됩니다.

### 5.7. 비-C# 언어의 데모 서명

**취약점:** 언어별 데모 프로그램(Go, Python, TS, Rust, Swift, Kotlin, C)은 시각화를 위해
정규적인 `BuildSignableData` 버퍼 대신 직렬화된 전체 와이어 바이트에 서명합니다. 해당
언어의 라이브러리 코드는 올바르지만 — 데모만 지름길을 사용하며, 포터에게 혼란을 줄 수
있습니다.
**완화 방법:** `OPEN_ISSUES.md` §10에서 추적됩니다. C# 데모의 3단계를 정규적인 플로우로
취급하십시오.
